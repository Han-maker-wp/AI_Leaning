| | 路线① transformers | 路线② Ollama | 路线③ vLLM |
|---|---|---|---|

## 1. 路线一：transformers 直接 generate

最朴素：加载模型 → 套 chat template → `generate`。价值在于**一切细节可控**（采样参数、
中间 logits、KV cache……），是做实验与理解原理的标准姿势。

```python
# 典型示例；接口与参数以 huggingface.co/learn 的 transformers 文档为准
# 国内先: export HF_ENDPOINT=https://hf-mirror.com
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "Qwen/Qwen2.5-0.5B-Instruct"          # 无 GPU 可用 0.5B；有 24G 卡可换 7B
tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    torch_dtype="auto",   # 按模型卡自动选 bf16/fp16；参数名随版本可能调整，以文档为准
    device_map="auto",    # 自动分配到可用设备（GPU/CPU/硬盘卸载）
)

messages = [
    {"role": "system", "content": "你是一个严谨的 Java 编程助手。"},
    {"role": "user", "content": "用一句话解释什么是反射。"},
]
text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tokenizer(text, return_tensors="pt").to(model.device)

out = model.generate(
    **inputs,
    max_new_tokens=200,
    do_sample=True, temperature=0.7, top_p=0.9,   # 采样参数详见 L03
    pad_token_id=tokenizer.eos_token_id,
)
print(tokenizer.decode(out[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True))
```

局限：吞吐低、无并发管理、进程即服务——只适合单机实验。真实应用请走②或③。

## 2. 路线二：Ollama——本地模型的「Docker」

Ollama 把「下载模型 + 量化 + 起服务 + 管理」打包成一条命令，默认拉取的即是量化版（GGUF），
所以下载体积与显存占用都是 int4 级（对照 L04：7B int4 ≈ 4~5GB）。

### 2.1 安装与基本使用

```bash
# 安装（官方脚本，以 ollama.com 安装页为准）
curl -fsSL https://ollama.com/install.sh | sh

# 拉取并进入交互对话（模型名以 ollama.com/library 为准）
ollama run qwen2.5:0.5b        # 0.5B，CPU 也流畅
# ollama run qwen2.5:7b       # 有 8GB+ 显存时的主力选择

ollama list                    # 已下载模型
ollama ps                      # 正在显存中运行的模型
ollama pull qwen2.5:1.5b       # 只下载不运行
```

### 2.2 REST API：本地 11434 端口

Ollama 跑起来后就是一个 HTTP 服务（默认 `http://localhost:11434`），两个核心端点（请求/响应
字段以 Ollama GitHub 仓库 docs/api.md 为准）：

```bash
# /api/generate：单轮补全式
curl http://localhost:11434/api/generate -d '{
  "model": "qwen2.5:0.5b",
  "prompt": "用一句话解释 KV Cache",
  "stream": false
}'

# /api/chat：多轮消息式（推荐，和你熟悉的 OpenAI 消息结构同构）
curl http://localhost:11434/api/chat -d '{
  "model": "qwen2.5:0.5b",
  "messages": [{"role": "user", "content": "写一个 Java 单例模式"}],
  "stream": false
}'
```

`stream: true`（默认）时返回 NDJSON——每行一个 JSON 增量片段，这正好对上你 Java Web 的流式
处理经验。

### 2.3 Java 集成（你的主场）

用 JDK 自带的 `java.net.http.HttpClient` 即可直连，无需任何 SDK。核心片段：

```java
// 完整可运行示例见 code/L05_ollama_java_client.md
HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("http://localhost:11434/api/chat"))
    .header("Content-Type", "application/json")
    .POST(HttpRequest.BodyPublishers.ofString("""
        {"model": "qwen2.5:0.5b",
         "messages": [{"role": "user", "content": "一句话解释 KV Cache"}],
         "stream": false}"""))
    .build();
HttpResponse<String> resp = HttpClient.newHttpClient()
    .send(request, HttpResponse.BodyHandlers.ofString());
// resp.body() 即 JSON 响应，解析 message.content 字段
```

局域网访问：设置环境变量 `OLLAMA_HOST=0.0.0.0` 后重启服务（以官方文档为准），你的
Spring Boot 应用就能调用局域网内任何一台机器上的 Ollama。

### 2.4 自定义模型（为阶段 5 埋伏笔）

`ollama create` + Modelfile 可以把**自己微调的模型**注册进 Ollama（阶段 5 L09 部署课的主角）。

## 3. 路线三：vLLM——生产级推理服务

vLLM 是当前开源高吞吐推理的事实标准。两个概念级关键词：**PagedAttention**（把 KV cache
像操作系统页表一样分页管理，减少碎片浪费）与 **continuous batching**（请求动态进出批，
GPU 永远吃满）——都是冲着并发吞吐去的。

### 3.1 启动（需 NVIDIA GPU）

```bash
# 安装（版本迭代快，以 vLLM GitHub 仓库 README 为准）
pip install vllm

# 启动 OpenAI 兼容服务（典型示例）
vllm serve Qwen/Qwen2.5-7B-Instruct \
    --host 0.0.0.0 --port 8000 \
    --gpu-memory-utilization 0.9 \
    --max-model-len 8192
# 新旧版本启动命令有差异（旧版为 python -m vllm.entrypoints.openai.api_server），以官方文档为准
```

`--gpu-memory-utilization`：允许 vLLM 使用的显存比例；`--max-model-len`：上下文上限（直接决定
KV cache 预留，L03/L04 的账在这里落地）。

### 3.2 调用：完全兼容 OpenAI API 格式

```bash
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen/Qwen2.5-7B-Instruct",
    "messages": [{"role": "user", "content": "一句话介绍你自己"}],
    "temperature": 0.7
  }'
```

**这是本课程最重要的工程接口**：OpenAI 兼容意味着你以前调 OpenAI 的所有代码（Java SDK、
Spring AI、curl 脚本）换个 base_url 就能指向自托管模型。完整速查见 `code/L05_vllm_quickstart.md`。

## 4. 三路线对比与选择

| 维度 | transformers | Ollama | vLLM |
|---|---|---|---|
| 上手成本 | 需写 Python | 一条命令 | 一条命令 + GPU |
| 量化内置 | 手动指定 | 默认 int4(GGUF) | 加载 AWQ/GPTQ 版模型 |
| 并发吞吐 | 无优化 | 低-中 | 高（批处理） |
| OpenAI 兼容 API | 无 | 自有 API | 有（/v1/...） |
| CPU 可用 | 可以（慢） | 可以 | 不面向 CPU |
| 什么时候用 | 实验/教学/改论文级细节 | 个人开发伴跑、桌面工具 | 应用后端、压测、生产 |

选择口诀：**白天写代码用 Ollama 伴跑，做毕业项目部署用 vLLM，做采样实验用 transformers。**

## 5. CPU vs GPU 的可行边界

结合 L04 显存账（int4 下显存换算 ≈ 内存需求）：

| 模型 | int4 内存需求 | CPU 体验 |
|---|---|---|
| 0.5B / 1.5B | <1 GB / ~1 GB | 流畅，可用 |
| 3B / 7B | ~1.6 GB / ~4-5 GB | 可跑；3B 尚可，7B 明显慢（个位数 token/s 级） |
| 14B+ | 7 GB+ | 慢到影响体验，只适合「偶尔问问」 |

结论：**CPU 适合 0.5B~3B 量化模型做原型验证**；7B 想要对话流畅基本需要 GPU；任何并发场景
（哪怕是 3~5 个用户）都应上 GPU + vLLM。这也是为什么 L06 算力决策课先算需求再选卡。

> 🍿 彩蛋｜把复杂度藏起来：在 Ollama 出现之前，本地跑模型要装 CUDA、下权重、配环境，劝退率极高；它把这一切压缩成一行 ollama run。工具的胜利常常不是算法的胜利，而是把复杂度藏起来的胜利——Spring 对 Servlet 做过同样的事。

## 小结与自测

1. **Q：三条路线各自的「一句话定位」？**
   A：transformers=可控的实验库；Ollama=本地模型管家（默认 GGUF 量化）；vLLM=高并发生产服务器。
2. **Q：为什么 Ollama 下载 7B 模型只有 4~5 GB？**
   A：默认拉取 int4 量化版（GGUF），对应 L04 公式 7×10⁹×0.5B≈3.5GB 加元数据。
3. **Q：vLLM 的两个核心优化是什么，各解决什么问题？**
   A：PagedAttention 解决 KV cache 显存碎片浪费；continuous batching 解决并发下 GPU 利用率。
4. **Q：「OpenAI 兼容」为什么对工程集成重要？**
   A：现有 OpenAI 客户端代码/SDK 换 base_url 即可无缝切换到自托管模型，避免供应商锁定。
5. **Q：8GB 内存的旧笔记本（无独显）能跑什么？**
   A：0.5B~3B 量化模型做原型；7B int4 勉强可载入但慢；并发场景不要考虑。
