# 第 7 课：Function Calling 与 RAG 概览（衔接你的 Agent 经验）
> 🎬 开场钩子：你作为 Agent 重度用户，早用熟了 function calling——但想过没有：模型到底「知道」自己在调函数吗？今天掀开应用层的天花板看看底下：模型输出的其实只是一段结构化文本，「调用」是你代码里的解析。知其所以然，才调得动更深的优化。


> ⏱ 建议学时：2 小时

## 本课目标

1. 能说清 function calling 的底层机制：模型输出结构化文本 → 应用层解析执行 → 结果回填的闭环。
2. 能解释为什么微调能提升 function calling 的遵循度与格式稳定性。
3. 能画出 RAG 全流程（chunking → embedding → 向量检索 → 拼上下文生成）并解释每步的取舍。
4. 能用「RAG vs 微调」决策表，为给定需求选出正确技术路线。
5. 理解两者组合使用的典型架构（微调教「怎么答」，RAG 给「答什么」）。

## 1. Function Calling 的真相：你早就在用，现在拆开看

你在 Agent 项目里已经熟练使用 function calling——本节把黑盒拆开，看模型侧到底发生了什么。

### 1.1 本质：特殊格式的生成 + 应用层执行

function calling **不是**模型「调用了函数」。模型从头到尾只做一件事：生成 token。
所谓调用，是一个闭环协议：

```
1. 应用把「可用工具的 schema 描述」注入 prompt（文本！）
2. 模型生成一段结构化文本，例如：
   {"name": "query_order", "arguments": {"order_id": "A123"}}
3. 应用层（你的 Java 代码）解析这段 JSON → 真正执行函数 → 拿到结果
4. 应用把结果作为 tool/observation 消息回填进对话
5. 模型基于结果继续生成（给出自然语言答案，或再次发起调用）
```

你过去写的「Agent 执行循环」，就是这个协议的应用层实现。模型的「能力」仅在于：它在 SFT
阶段见过大量此类数据，学会了**在合适的时机、按约定的格式**输出工具调用。

### 1.2 模型侧的训练支撑

- chat 模型的 SFT 数据里包含工具调用轮次（工具描述 → 模型调用 → 工具结果 → 模型总结），
  所以它「认识」这种格式约定——和 chat template 是特殊 token 约定（L03）一个道理。
- 推理侧还有 **constrained decoding（约束解码）** 技巧：在生成 JSON 时限制只能输出合法
  token（比如只允许字符集中出现合法 JSON 字符），把「格式合法」从概率问题变成机制保证。
  概念了解即可。

### 1.3 为什么微调能提升 function calling

这是阶段 5 与你的直接关联。通用模型的 FC 训练数据覆盖的是「常见通用工具形态」；当你的场景是：

- 一套**私有 API/工具集**（你们公司的订单系统、内部 DSL）
- 特殊的调用规范（必须先 A 后 B、参数间依赖）
- 小模型跑边缘部署，指令遵循能力不足

……通用模型的遵循度就会打折。**用你自己的工具调用轨迹做 SFT 数据**微调后，模型对「这套
schema 的调用时机与格式」显著更稳——本质还是那句话：微调教行为。毕业项目若选 Java 代码
助手，「让模型稳定输出某种结构（如 patch 格式）」就是同一原理的应用。

## 2. RAG 原理流程

RAG 你在应用层用过，本节补上原理视角与每步的「为什么」。

```
离线（建索引）：
  文档集合 → 切分 chunking → 逐 chunk 算 embedding → 存入向量库
在线（问答）：
  用户问题 → 算 embedding → 向量检索 top-k 相似 chunk → 拼进 prompt → LLM 生成答案
```

### 2.1 chunking：切多大是门学问

- 太大：一个 chunk 混多个主题，检索命中了但噪声多；能塞进上下文的 chunk 数也变少。
- 太小：语义被切碎，单看一个 chunk 不知所云。
- 经验起点：几百 token 一个 chunk，带少量重叠（overlap），然后**按你的文档结构调**——
  Java 代码按类/方法切，合同按条款切，比任何通用参数都强。

### 2.2 embedding：语义 → 向量

embedding 模型把文本映射为定长向量，**语义相近则向量夹角小**（余弦相似度）。关键直觉：
它做的是「模糊语义匹配」，不是关键词匹配——「退货政策」能召回「如何办理退款」，靠的就是
两者在这个向量空间里距离近。开源常用如 BGE 系列中文模型（HF 可下载，配合 sentence-transformers
使用很方便）。注意：embedding 模型与生成模型是两个独立的小模型，别混为一谈。

### 2.3 向量库：相似度的索引工程

向量库解决「在百万向量里毫秒级找出 top-k 最近邻」。概念级认识即可：

- FAISS：Meta 的向量检索**库**（嵌入式，适合单机原型）
- Milvus / Chroma：向量**数据库**（服务化、可扩展）
- pgvector：PostgreSQL 插件——对你这种 Java/数据库背景的工程师，往往是最平滑的入门选择

### 2.4 检索之后

top-k chunk 拼进一个 prompt 模板（「请仅根据以下资料回答……」），交给 LLM 生成。采样参数
建议低温（L03 表：RAG 引用式回答用 T≈0~0.2，减少自由发挥）。

## 3. RAG vs 微调：选型决策表

这张表是本课的核心交付。先建立总原则：**RAG 改变模型「知道什么」，微调改变模型「怎么表现」**。

| 维度 | RAG | 微调（SFT/LoRA） |
|---|---|---|
| 解决什么 | 知识注入（时效性、私有库） | 行为塑造（格式、风格、遵循度、领域话术） |
| 知识更新 | 改文档重索引即可，分钟级 | 重训（小时级）+ 数据更新成本 |
| 一次性成本 | 低（无需训练） | 中（数据构建是主要成本） |
| 推理时成本 | 每次多一路检索 + 更长 prompt | 与原模型相同 |
| 精确事实/可追溯 | 强（可给出引用出处） | 弱（知识混在权重里，可能幻觉） |
| 改变输出格式/风格 | 弱（prompt 约束有限） | 强（这是微调的主场） |
| 长尾私有知识 | 强 | 数据不够时学不会 |
| 小模型提速降本 | — | 蒸馏大模型行为到小模型 |

### 三个判断题（先自己做再对答案）

1. 「客服要按我们公司规定的语气和流程回复」→ **微调**（行为/风格是权重里的事）。
2. 「答案必须来自每周更新的产品手册」→ **RAG**（知识高频变化 + 可溯源）。
3. 「让模型稳定输出我们内部 API 的调用 JSON」→ **微调**（格式遵循度），执行仍在应用层。

### 组合使用是常态

生产系统常见架构：**微调后的领域模型 + RAG 知识层**——微调教它「像个领域专家一样说话和
调用工具」，RAG 在每次回答时递给它「今天最新的资料」。你的毕业项目（如领域客服）可以只做
微调，但答辩时能说清「哪些问题该留给 RAG」是加分项。

你已经具备的应用层经验（function calling 循环、RAG 调用）+ 本课的原理视角 + 阶段 4 的

## 小结与自测

1. **Q：function calling 中模型真正做了什么？**
   A：只生成结构化文本（约定的 JSON）；解析与执行全部发生在应用层，结果再回填给模型。
2. **Q：为什么微调能提升 FC 遵循度？**
   A：SFT 数据含工具调用轨迹，模型学会针对你的 schema 在正确时机输出正确格式——行为塑造。
3. **Q：RAG 四步流程？**
   A：chunking → embedding 入库 → （在线）query embedding 检索 top-k → 拼上下文生成。
4. **Q：一句话区分 RAG 与微调的适用问题？**
   A：RAG 解决「知道什么」（时效/私有知识），微调解决「怎么表现」（格式/风格/遵循度）。
5. **Q：为什么说两者常组合使用？**
   A：微调给行为与话术，RAG 给实时知识，二者正交互补，生产系统常同时部署。
