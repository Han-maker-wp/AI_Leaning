# 第 6 课：超参与显存管理
> 🎬 开场钩子：为什么 LoRA 的学习率比全参微调大一个数量级？为什么 epoch 一多模型就开始「背题」？今天讲的每个旋钮都有明确理由——调参不是玄学，是有公式和清单的工程。学完这课，你调参的样子会从「拜佛」变成「看仪表盘」。


> ⏱ 建议学时：2.5 小时

## 本课目标

1. 掌握微调超参基线与调节直觉：lr / epochs / 等效 batch / cutoff_len / warmup。
2. 能解释「LoRA 学习率比全参高一个量级」的原因。
3. 拿到 OOM 报错能按排查清单逐项定位解决。
4. 会用 nvidia-smi 读数做训练期监控与显存余量管理。
5. 会处置 loss NaN（定位三类常见根因）。

## 1. 超参基线与调节直觉

先给基线（7B QLoRA、几百~两千条数据的典型起点），再逐个讲「为什么」与「怎么调」：

| 超参 | 基线 | 调节方向 |
|---|---|---|
| learning_rate | 1e-4（LoRA 典型 1e-4~2e-4） | loss 不降→略升；loss 震荡/NaN→降 |
| num_train_epochs | 2~3 | 过拟合→减；没学够→加（优先加数据） |
| per_device_batch × 梯度累积 | 1×8=8 等效 | 见下文，用「等效 batch」思考 |
| cutoff_len | 1024~2048 | 按数据长度分布定 |
| lora_rank / alpha | 8 / 16 | 一般不动；L03 说了 r 不敏感 |
| warmup_ratio | 0.05~0.1 | 固定常用值即可 |
| lr_scheduler_type | cosine | 默认即可 |

### 1.1 学习率：为什么 LoRA 要比全参高一个量级

全参微调 7B 的典型 lr 在 1e-5~2e-5 量级，LoRA 却用 1e-4~2e-4。直觉拆解：

- 全参更新时，动的是千亿个「已经调好」的参数——步子必须极小，否则破坏预训练分布
  （灾难性遗忘的学习率版本）。
- LoRA 更新的只有 $BA$ 这一小撮**从零起步**的参数（B 零初始化），且更新的是「增量」而非
  主干本身——同样的步长对模型行为的扰动小得多，可以用大步长快速收敛。

类比（Java 视角）：全参微调像在生产代码上直接 hotfix，改一行都要评审三遍；LoRA 像新开分支
开发 feature，大胆提交，主干（冻结的 W）永不污染。

调节信号看 loss 曲线（L05 §5）：降不动→升一档（×2）；震荡或 NaN→降一档（×0.5）。

### 1.2 epochs：指令微调极易过拟合

指令数据量小（几百~几千条）、LoRA 学得快，epoch 一多模型就开始「背训练集」：
train loss 漂亮地降下去，对话却变得死板、复读、离开领域就翻车（L10 坑课详解）。
基线 2~3 个 epoch，**宁可欠一点，不要过**；效果不够先怀疑数据和评估（L07），不是加 epoch。

### 1.3 batch_size × 梯度累积 = 等效 batch

小显存跑不了大 batch，于是用梯度累积：每 8 个 micro-batch 攒一次梯度再更新——数学上
约等于 batch=8 的单次更新（除掉 BN 等细节，LLM 训练无此问题）。等效 batch 的直觉：

- 太小（1~2）：梯度噪声大，loss 曲线抖
- 太大（64+）：几百条数据的微调每 epoch 没几步更新，学不到东西；显存也吃不消
- 经验区间：**8~32**，微调小数据常用 8~16

### 1.4 cutoff_len 与长样本

cutoff_len 是样本 tokenize 后的截断长度：

- **过短**：长样本（比如整个类的代码）被拦腰截断，output 被切掉一半——模型学到的是
  「半截答案」，纯毒药
- **过长**：激活显存与训练时长线性上涨（阶段 4 L03/L04 的账）

正确做法：先用 tokenizer 统计数据长度分布（p95/p99），cutoff_len 取「覆盖 95% 以上样本」
的值，剩下的超长样本单独处理（拆分或丢弃）。

### 1.5 warmup 与 scheduler

warmup：前 5~10% 步从 0 线性升到目标 lr——训练初期梯度方向不可靠，直接全速容易把 B 矩阵
带偏（你手写 GD 时「前几步 loss 反而升」的记忆就是同一现象）。cosine 衰减让收尾阶段小步
精修。两者都用默认配置即可，不是你的调参重点。

## 2. 显存管理实操

### 2.1 OOM 排查清单（按性价比排序）

训练报 `CUDA out of memory` 时，按序尝试（每一项单独改，改一项跑一次）：

1. **降 per_device_train_batch_size**（如 2→1）——最立竿见影
2. **减 cutoff_len**（如 2048→1024）——第二立竿见影（激活随长度降）
3. **开梯度检查点（gradient checkpointing）**：用约 20%~30% 的重计算换激活显存大降
   （LLaMA-Factory 配置项 `gradient_checkpointing: true`，参数名以官方文档为准）——
   训练变慢但能省大块显存，微调场景几乎总是值得
4. **降 lora_rank / 减 lora_target 范围**——收益小（LoRA 本身就小），最后才考虑
5. 确认已是 QLoRA（quantization_bit: 4）且 bf16/fp16 开启（别用 fp32 训练！）
6. 框架兜底：QLoRA 的分页优化器（paged optimizer 选项，见官方文档）

反直觉提醒：**OOM 常发生在第一步或第一个 epoch 边界**（遇到最长样本时），不是稳定状态。
所以 L05 的「空跑几个 step」不一定能暴露长样本问题——统计长度分布才是根治。

### 2.2 nvidia-smi 监控读数（训练期）

```bash
watch -n 1 nvidia-smi     # 或 nvidia-smi -l 1
```

- **Memory-Used 曲线**：健康状态是快速上升后**稳定在峰值下方**。持续爬升不回落 =
  有显存泄漏（通常是缓存堆积，重启进程解决）
- **余量纪律**：峰值与上限保持 ≥10% 余量，防止评估/保存时的临时峰值补刀
- **GPU-Util**：长期 <50% → 数据加载瓶颈或 batch 太小（IO 慢时把数据预处理打开
  preprocessing_num_workers）

### 2.3 训练前显存预算（把 L04 的账落成习惯）

开训前口算一遍（7B QLoRA 为例）：权重 3.5 + LoRA 全套 0.5 + 激活（batch×len 决定，1×2048 约
2~4GB）+ 框架 1~2 ≈ **7~10GB**。口算超过卡的显存，先做 2.1 的 1~3 项再开训。

## 3. loss NaN 处置

NaN = 数值系统崩了，按三类根因排查（按概率排序）：

1. **学习率过大**（最常见）：loss 在 NaN 前通常先震荡放大。处置：lr 减半再试；确认
   warmup 已开启。
2. **数据坏样本**：超长样本、乱码、全空 output 等。处置：用 `data_clean.py` 加严过滤；
   二分法定位——max_samples 分段训练，看 NaN 出现在哪段数据。
3. **精度问题**：fp16 下溢/溢出（阶段 4 L04：fp16 范围窄）。处置：换 bf16（卡支持的话）；
   老卡只支持 fp16 时降 lr 并检查是否可换模型/精度配置。

NaN 出现后先「缩 lr」是经验上的第一反应，八成能止住。

## 4. 一页调参手册（贴墙版）

```
loss 不降        → lr ×2 / 查数据是否太脏 / 查 template 是否正确
loss 震荡        → lr ×0.5 / 增大等效 batch / 确认 warmup
loss → 0         → 过拟合：epoch 减 1 / 加数据 / 早停
对话变笨/复读     → 同上（过拟合），另查是否混入坏数据
OOM             → batch↓ → cutoff↓ → 梯度检查点 → rank↓
NaN             → lr↓ → 查坏样本 → bf16
没学够(欠拟合)    → epoch+1 / lr 略升 / 换更大 r 收益有限,优先查数据覆盖度
```

> 🍿 彩蛋｜炼丹黑话的由来：深度学习圈把调参叫「炼丹」、把显卡叫「丹炉」——因为很多超参没有理论最优，只有实验直觉。但炼丹师和烧炉工的区别，在于前者知道为什么要加这味药。这课给你的就是「药理」。

## 练习

1. 写一段脚本：用 Qwen tokenizer 统计你数据集 token 长度的 p50/p95/p99，据此确定你的
   cutoff_len 并说明理由。
   提示：对每条样本渲染 chat template 后再统计（template 会加几十个 token）。
2. 复现一次 OOM 并解决：把 batch_size 与 cutoff_len 故意调大触发 OOM，再按 2.1 清单逐项
   恢复，记录每项各省了多少显存（看 nvidia-smi 峰值）。
   提示：梯度检查项那一步的显存下降最明显，耗时增加也最明显，把两个数字都记下。
3. 判断题（每题 2 句理由）：a) lr 2e-5 对 LoRA 来说偏小；b) epoch 越多效果越好；
   c) 等效 batch=2 一定比 8 差。
   提示：a 对（LoRA 要高一档）；b 错（过拟合）；c 不一定（数据很少时小 batch 步数更多）。
4. 模拟排障：训练 40 分钟后突然 NaN，前 40 分钟 loss 正常下降。列出你的排查顺序。
   提示：先想「40 分钟处发生了什么」——大概率撞上长样本或坏样本；查该 step 的样本。

## 小结与自测

1. **Q：LoRA 的 lr 为什么比全参高一个量级？**
   A：只更新从零起步的增量参数且主干冻结，大步长对模型扰动可控；全参动的是调好的权重，
   必须小步。
2. **Q：等效 batch 怎么算？为什么微调不宜太大？**
   A：per_device_batch × 梯度累积；数据少时大 batch 每 epoch 更新步数太少，且显存吃不消。
3. **Q：cutoff_len 过短的危害？怎么定？**
   A：长样本 output 被截断，模型学半截答案；按 tokenize 后长度分布的 p95 定。
4. **Q：OOM 排查前两步？**
   A：降 per_device_batch_size，减 cutoff_len；再考虑梯度检查点。
5. **Q：loss NaN 的第一反应？**
   A：学习率减半（最常见根因），并确认 warmup 开启；不行再查坏样本与精度。
