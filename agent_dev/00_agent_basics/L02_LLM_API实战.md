# 第 2 课：LLM API 实战——messages、流式与 token

> 🎬 开场钩子：你以为的"打字机效果"是模型边想边给你？其实每一段生成到一半的文本，都是服务端通过一个比 WebSocket 老得多的技术——SSE——实时推给你的。而你等待的真正大头，不是"打完这些字"，而是第一个字出现之前的漫长沉默。搞懂流式、消息结构、token 这三件事，你和模型之间的每一毫秒、每一分钱就都没有黑盒了。

⏱ 建议学时：2 小时（`code/L02_api_demo.py` 必须亲手跑）

## 本课目标

1. 说清「OpenAI 兼容端点」是什么、为什么它让你一行代码换模型供应商
2. 正确构造多轮 messages，解释 API 为什么是无状态的、历史为什么要全量重发
3. 实现流式输出并统计首 token 延迟，说清 SSE 与 WebSocket 的区别
4. 从 usage 字段读取 token 消耗，估算一次调用与一轮会话的成本

## 2.1 OpenAI 兼容端点：一套事实标准

调 LLM 的 HTTP 接口长什么样？行业现状是：OpenAI 的 Chat Completions 接口成了**事实标准**，国内外大量平台（大模型厂商、聚合网关、本地推理服务）都提供"兼容端点"——同样的请求路径、同样的参数结构、同样的响应格式。于是 openai 这个 SDK 变成了通用客户端：

```python
from openai import OpenAI

# 连官方
client_a = OpenAI(api_key="...")
# 连任意兼容端点：只多一个 base_url，其余代码一字不改
client_b = OpenAI(api_key="...", base_url="https://某个兼容平台地址/v1")
```

这就是本轨道代码统一用 `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` 三个环境变量的原因——**换供应商 = 换环境变量，代码零改动**。具体地址、模型名、参数支持度以你所用平台的文档为准（OpenAI 侧以 platform.openai.com/docs 为准）。

> ☕ Java 视角：这就是 JDBC 的故事——Sun 定接口，各厂商出驱动，你写 `DriverManager.getConnection(url)`。兼容端点是 LLM 界的 JDBC：openai SDK 是接口层，base_url 是连接串。所以别把 `from openai import OpenAI` 理解为"绑定 OpenAI 公司"，它绑定的是一套协议。

## 2.2 messages：对话的真实形态

模型看到的不是"一句话"，是一个**消息列表**，每条带角色：

```python
messages = [
    {"role": "system",    "content": "你是一个简洁的技术助手"},   # 全局设定（开发者写）
    {"role": "user",      "content": "什么是 REST？"},            # 用户输入
    {"role": "assistant", "content": "REST 是一种架构风格……"},    # 模型历史回复
    {"role": "user",      "content": "和 GraphQL 有何区别？"},    # 新输入
]
```

三个要点，每个都值回票价：

1. **API 是无状态的**。服务端不记得你，"多轮对话"的连续感是错觉——每次请求你都把全部历史重发一遍。这解释了为什么长对话越来越贵（历史越长，输入 token 越多），也埋下了阶段 1 L04「记忆管理」的伏笔。
2. **assistant 消息不是装饰**。它是你替模型"认领"的历史发言。不带上它，模型会把"和 GraphQL 有何区别"当成新话题——指代全部失效。
3. **system 是契约位**。角色、语气、输出格式、边界都写在这里，它对后续所有轮次生效。L03 整课讲怎么写好它。

返回值里另一个值得盯的字段是 `finish_reason`。常见取值与应对——

| finish_reason | 含义 | 你该做什么 |
|---|---|---|
| `stop` | 正常说完 | 正常走流程 |
| `length` | 被 max_tokens 截断 | 开大上限，或把任务拆小（长文总结分段做） |
| `tool_calls` | 模型想调工具（阶段 1 主角） | 转入工具执行分支 |

（取值集合以官方文档为准，不同版本可能扩充。）

> ☕ Java 视角：把 messages 想成一个显式传递的 `List<ChatMessage>` 会话 DTO——没有 server-side session，客户端全权负责状态。习惯了 HttpSession 的你要反转心智：状态在调用方手里，这是后面一切记忆管理的出发点。

## 2.3 流式输出：SSE 的文艺复兴

默认调用是"等全部生成完再返回"。把 `stream=True` 传进去，行为变为：服务端生成了一个 token 就推一个，你的 `for` 循环逐段拿到 `delta.content`：

```python
stream = client.chat.completions.create(model=model, messages=messages, stream=True)
for chunk in stream:
    piece = chunk.choices[0].delta.content   # 增量片段，可能为 None（如仅携带元信息的块）
    if piece:
        print(piece, end="", flush=True)
```

传输技术是 **SSE（Server-Sent Events）**：一条普通 HTTP 长连接上，服务端按 `data: {...}\n\n` 的格式持续写事件，浏览器/客户端逐条解析。它和 WebSocket 的区别值得记牢——SSE 单向（只能服务端推）、基于纯 HTTP（网关/代理/鉴权全兼容）、断线自动重连是协议内建语义；WebSocket 双向、独立协议、需要升级握手。LLM 场景只需要"服务端单向吐 token"，SSE 恰好够用且最省事，于是这个曾坐了多年冷板凳的技术一夜翻红。

流式的工程价值不只是好看：**首 token 延迟（Time To First Token）是交互体验的核心指标**——用户在 0.5 秒看到第一个字就开始阅读，比 8 秒后看到完整答案的体感好得多。`code/L02_api_demo.py` 里有现成的测量方法。

> ☕ Java 视角：Spring 里的 `SseEmitter`、WebFlux 的 `Flux<ServerSentEvent>` 就是同一套东西。你在 Web 主场早就会了，这里只是从"服务端写"换到"客户端读"。

补充一个流式实现细节：`flush=True` 别省——终端默认缓冲输出，不加它"打字机"会退化成"一段一段蹦"；Web 端同理，SSE 事件被代理缓冲住，用户看到的就不是流式（阶段 4 服务化时会用响应头解决它）。

## 2.4 token 与计费：账单的算法

**token 是模型处理文本的最小单元**，由分词器（tokenizer）切出——既不是字符也不是单词。英文大约一个常见词一 token；中文经验上一个汉字常落在 1~2 token 区间（不同分词器差异很大，以各家 tokenizer 工具为准）。你在产品里见过"上下文限制 128k"之类的话吗？单位全是 token。

计费公式很简单，但两个单价经常被忽略：

```
成本 = 输入 token 数 × 输入单价 + 输出 token 数 × 输出单价
```

- **输出单价通常数倍于输入单价**——让模型"少废话"不只是体验问题，是钱的问题
- **每轮对话都为全部历史再付一次输入费**：第 10 轮会话的一句"好"，要把前 9 轮全部重发。对话越长，单轮成本越高——这是记忆压缩（阶段 1 L04）的经济动机
- 响应里的 `resp.usage` 给出精确账单：`prompt_tokens` / `completion_tokens` / `total_tokens`，代码里永远以它为准，别自己估

> 🍿 彩蛋｜为什么按 token 不按字收费：模型训练和推理的计算量都正比于 token 数（Transformer 要对每个 token 做 attention，见主线阶段 3 精读的 arXiv 1706.03762），token 是模型世界真正的"流量单位"。计费跟着成本走，天经地义。

## 2.5 顺手认识两个常用参数

`create()` 还有两个你会天天打交道的参数（取值范围以官方文档为准）：

- **`temperature`**：采样随机性。低值（如 0-0.3）输出更稳定保守，适合分类、抽取、JSON 输出等"要确定性"的任务；高值更发散多样，适合创意写作。工程默认：结构化任务低温，创作任务中高温
- **`max_tokens`**：单次响应的输出上限。它同时是"成本护栏"和"截断风险"——设太小回答被腰斩（finish_reason=length），设太大失控输出烧钱。给每类任务设一个合理上限是成本管理的基本功

这两个参数加上 `stream`，是你现阶段需要掌握的全部请求参数——**API 面小而稳定，这是它作为"标准协议"的优点**。

## 2.6 跑通 code/L02_api_demo.py

配套脚本把本课三块内容串成一个可复用的实验台（无 key 时会打印设置指引后退出）：

## 2.7 常见错误与第一反应

调用失败是常态而非例外，先建立"看错误分类处理"的反射：

| 现象 | 通常原因 | 第一反应 |
|---|---|---|
| 401 / 403 | key 错误、没权限、环境变量没注入 | 检查 key 与环境变量；别急着改代码 |
| 404 | base_url 写错（路径少了 `/v1` 之类） | 打印实际请求的地址核对 |
| 429 | 速率限制（RPM/TPM 超额） | 指数退避重试（L05 详攻），别硬顶 |
| 5xx | 服务端抖动 | 可重试，连续失败则检查平台状态页 |
| 请求超时 | 网络或服务端排队 | 设客户端超时 + 重试，别无限等 |
| 返回空 content | 被安全策略拦、或命中格式约束 | 打印 finish_reason 判断，别当 bug 瞎猜 |

工程习惯：把"无 key / 网络不通 / 限流 / 服务端错误"四类出口都写成友好提示（`code/L02_api_demo.py` 的 main 里留了兜底范例）——你迟早要做 checkpoint 的"断网不裸抛栈"，现在顺手养成。

## 小结与自测

- 问：为什么说 chat API 是无状态的？答：服务端不存任何会话，多轮对话靠客户端每次全量重发 messages。
- 问：兼容端点解决什么问题？答：统一协议让 SDK 与代码可复用，换供应商只换 base_url 与 key。
- 问：SSE 与 WebSocket 的核心区别？答：SSE 基于纯 HTTP 单向推送、网关友好；WebSocket 是双向独立协议，LLM 流式只需前者。
- 问：为什么长对话越来越贵？答：每轮都要为全部历史付输入 token 费，且输出单价高于输入。
- 问：怎么拿到精确 token 数？答：读响应的 usage 字段，不要自己估算。
