# 第 3 课：提示工程（开发者视角）——prompt 就是你给模型的 API

> 🎬 开场钩子：产品经理眼里的提示工程是"念咒"——玄学措辞、emoji 加持、转发这条锦鲤。开发者眼里的提示工程朴素得多：prompt 是**你写给模型的一份接口契约 + 默认配置**。你写 javadoc 的全部功力在这里直接复用；反过来，"试出来一次好用的咒语"不写进版本管理，等于上线没提交代码。

⏱ 建议学时：1.5 小时

## 本课目标

1. 说清 system / user / assistant 三种角色的职责边界，以及为什么开发者只控制其中两种
2. 用 few-shot 而不是形容词规则来约束输出，并解释为什么前者更有效
3. 解释思维链起作用的机制，并能在结构化输出场景里正确使用它
4. 把 prompt 当代码管理：变量模板化、进版本库、可测试

## 3.1 角色的真实语义：契约位与输入位

L02 见过 messages 的三种角色。开发者视角下它们的分工是：

| 角色 | 谁写 | 类比 | 变更频率 |
|---|---|---|---|
| system | 开发者 | 接口契约 + 全局配置（过滤器里设的字符集） | 随代码发版 |
| user | 终端用户 | 请求体 | 每次请求 |
| assistant | 模型（历史） | 响应的历史回放 | 每轮追加 |

这个分工决定了两条纪律：

1. **凡是"规则"，一律进 system，不要拼在 user 里**。"请用中文回答"写在 system 里对全程生效；拼在用户输入后面，既可能被第 3 轮遗忘，也可能被用户自己的输入覆盖。
2. **不要信任 user 输入，也不要让它改变契约**。用户说"忽略你的设定"就能改变助手行为吗？这正是 prompt injection 的雏形——阶段 1 L05 与阶段 4 L03 会反复回到这个战场。现在先记住结构上的防御：契约（system）与数据（user）分离。

> ☕ Java 视角：这就是"配置与输入分离"的老规矩——你会把业务规则写进 web.xml/配置类，而不会让 query string 决定事务隔离级别。system 是配置，user 是输入，越界的输入就是攻击面。

## 3.2 few-shot：例子是最高效的需求文档

想让模型把用户邮件分成三类，两种写法：

```
写法 A（形容词流）：请将邮件分类为"咨询/投诉/合作"，分类要准确、风格要专业……

写法 B（few-shot）：
邮件：你们这个破系统又崩了，我要退款！
分类：投诉
邮件：请问企业版支持私有化部署吗？
分类：咨询
（再来 1-2 组，覆盖每类与边界情况）
```

写法 B 几乎总是更稳。原因不神秘：模型的本质是**从分布中模仿**——你给它若干"输入→输出"对，它内插这个映射；而你给形容词，它只能按自己对"准确""专业"的理解自由发挥，每个人的理解还都不一样。工程上的推论：

- 例子的**格式**比内容更早被学会——输出格式的 few-shot 是 L04 结构化输出的地基
- 例子要**覆盖边界**（投诉里夹带咨询、空邮件、两类混合），模型对没见过的类别边界自有一套放飞的理解
- few-shot 不是免费的：每轮请求都带着这些例子，**token 持续计费**。例子够用就好，能进 system 的进 system（不随对话变的部分）

> 🍿 彩蛋｜行业黑话里管这叫 in-context learning（上下文学习）：不训练、不改参数，仅凭上下文里的例子就改变行为——大模型最重要的"涌现"能力之一，也是"Agent 不微调也能定制"的前提。主线微调轨道教的是另一条路：改参数。两条路何时选哪条，阶段 2 L01 有专门一节。

## 3.3 思维链：给模型更多工作内存

对复杂任务（多步推理、数学、规则叠加），在指令里加一句"先一步步分析，再给最终答案"，正确率往往显著提升。这就是思维链（Chain-of-Thought，CoT）。

机制值得说透，因为它影响后面所有设计决策：模型生成是逐 token 的，**前面生成的中间推理文本会成为后续 token 的上下文**——相当于模型把中间结论"写进草稿纸"，再基于草稿作答。不写草稿直接作答，等于心算多位数乘法：不是不会，是工作内存不够。

用 CoT 时注意与输出格式的张力：

```
请按以下两段输出：
【分析】一步一步推理，说明依据
【答案】只输出一个 JSON 对象，字段：verdict(支持/不支持), confidence(0-1)
```

先推理后结构化，两段各司其职。**不要**让模型"直接输出 JSON 且内含推理过程"——推理文字混进 JSON 是解析事故的头号来源（L04 的容错解析救的就是它）。

> ☕ Java 视角：CoT ≈ 让计算过程溢出到磁盘而不是全靠 CPU 寄存器。寄存器（隐式注意力）容量有限，写出去的草稿（显式 token）可以被反复引用。阶段 1 的 ReAct 模式（arXiv 2210.03629）把这个思想推到极致：草稿纸不但记推理，还记"下一步动作"。

## 3.4 输出格式约定：写给解析器看的句子

你的下游代码要解析模型输出，所以格式约定不是"给用户看的排版"，是**接口契约**。四条经验法则：

1. **明确到无歧义**："输出 JSON" 不如 "只输出一个 JSON 对象，不要 markdown 代码块，不要任何解释文字"
2. **给出 schema 而非描述**：直接在 prompt 里写字段清单、类型、枚举值、缺失语义（`"category": "投诉|咨询|合作，无法判断填 unknown"`）
3. **给一个输出示例**（few-shot 与格式约定的合体，比十行描述管用）
4. **约定冲突裁决**："若信息不足，宁可填 null，不要编造"——这句话同时是 L04 校验与阶段 2 忠实度的伏笔

但要清醒：**约定只是君子协定，模型不保证遵守**（越小的模型越不保证）。L04 的三层防御把"君子协定"升级成"合同+验收"。

## 3.5 prompt 的工程化管理

最后一块拼图：prompt 是代码。三件事立刻做起来：

```python
"""把 prompt 收敛成函数：变量显式、可单测、可进 git。"""
from string import Template


def classify_email_prompt(email_text: str) -> list[dict]:
    """生成邮件分类的完整 messages。改契约只改这里，有 diff 可 review。"""
    system = (
        "你是客服邮件分类器。只输出 JSON：{\"category\": \"咨询|投诉|合作|unknown\"}。\n"
        "信息不足以判断时填 unknown，不要猜测。\n"
        "示例：\n输入：你们系统又崩了，退款！\n输出：{\"category\": \"投诉\"}"
    )
    user = f"输入：{email_text}\n输出："
    return [{"role": "system", "content": system}, {"role": "user", "content": user}]


if __name__ == "__main__":
    for m in classify_email_prompt("请问可以开增值税专用发票吗？"):
        print(m["role"], "=>", m["content"][:40], "...")
```

- **版本化**：prompt 改一个词，行为可能大变。进 git，改动走 review，别在生产环境手改
- **模板化**：变量注入统一走函数/模板（f-string、`string.Template` 均可），杜绝散落各处的字符串拼接
- **可测试**：固定输入 → 断言输出可被解析/分类正确。这套断言长大后就成为阶段 4 的评估（Evals）体系

> ☕ Java 视角：把 prompt 函数当成你写的 `buildRequest()`——纯函数、入参出参明确、有单测。最忌讳的是把 prompt 写成"运行时随手拼的字符串"，那是 LLM 界的 SQL 注入式坏味道。

## 3.6 常见反模式速查

| 反模式 | 症状 | 改法 |
|---|---|---|
| 规则拼在 user 里 | 第三轮开始规则"失忆" | 规则全部进 system |
| 形容词流约束 | 输出时有时无地符合"简洁" | 换 few-shot 示例 |
| 万能 prompt | 一个 prompt 又翻译又分类又写诗 | 按任务拆分，各配各的契约 |
| 咒语堆叠 | "请务必一定要严格"复读机 | 一条明确指令胜过十条强调 |
| prompt 不进版本库 | 线上行为莫名变化无法回溯 | prompt 当代码进 git |
| 隐式依赖记忆 | "按上面说的格式"（上一轮的格式） | 每轮把 schema 重申进 system |

这些症状的共同根源：**把 prompt 当聊天记录而不是接口**。评审自己的 prompt 时拿一个问题问："如果这是一个 REST 接口的契约文档，这么写能过评审吗？"——不能过就改。

## 3.7 一页评审清单：prompt 也要 code review

给自己的 prompt 过一遍（checkpoint 与以后的生产代码同用）：

- [ ] 规则全在 system；user 只承载数据，无法改写契约
- [ ] 输出格式有显式 schema 与示例，且示例与 schema 完全一致
- [ ] few-shot 覆盖了边界情况（含"无法判断"类样例）
- [ ] 冲突裁决已约定（信息不足时填什么、绝不允许编造）
- [ ] 推理与答案分离（先分析段后答案段，别混进同一个 JSON）
- [ ] prompt 收敛成函数，变量显式，进了 git
- [ ] 有至少三条固定输入的冒烟用例（能解析/能分类/格式稳定）

第七条是分水岭：有冒烟用例的 prompt 才算工程资产，否则只是某次好运的聊天记录。

## 练习

1. 为"技术支持工单分类器"写完整 messages：system 契约 + 3 个 few-shot（含一个边界例）+ 格式约定。
   提示：先定 JSON schema 再写例子，保证例子与 schema 完全一致。
2. 设计一个 10 题的小实验，对比"直接作答"与"先分析再作答"的正确率差异（题型选多步推理类）。
   提示：把两种 prompt 各跑一遍同样的 10 题，人工判分记录正确数即可。
3. 把练习 1 的 prompt 重构成 3.5 的函数模板形式，并用 3 条固定输入验证输出格式稳定。
   提示：断言输出能通过 `json.loads`（哪怕偶发失败，记录次数——这个失败率就是 L04 的动机）。

## 小结与自测

- 问：为什么规则要进 system 而不是拼在 user 里？答：system 是契约位、全程生效；拼在 user 里易被覆盖、易遗忘，且混淆了配置与输入的边界。
- 问：few-shot 为什么比形容词有效？答：模型靠模仿分布工作，"输入→输出"对给出了精确映射，形容词留给模型自由解释的空间。
- 问：思维链为什么有效？答：中间推理 token 成为后续生成的上下文，相当于把工作过程写到草稿纸上，缓解一步到位的工作内存压力。
- 问：格式约定有哪四条法则？答：明确无歧义、给 schema、给示例、约定冲突裁决（宁 null 勿编造）。
- 问：prompt 为什么要函数化+进 git？答：行为随措辞变化，函数化才能变量显式、可测试、可 review、可回滚。
