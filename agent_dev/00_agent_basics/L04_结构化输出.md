# 第 4 课：结构化输出——从自然语言到可靠数据

> 🎬 开场钩子：模型说："好的，以下是您要的 JSON："——然后给了你一个 markdown 代码块包着的、带行尾注释的、最后一个字段后面拖着逗号的 JSON。`json.loads` 当场炸裂。每个 Agent 开发者的第一次崩溃都长这样；今天这课后，你的解析器从此免疫这三种（以及更多）花式翻车。

⏱ 建议学时：2 小时（`code/L04_structured_output.py` 无 key 可跑，务必动手）

## 本课目标

1. 说清三层防御（API 层 / 约定层 / 校验层）各自挡什么、为什么默认组合是约定+校验
2. 会用 Pydantic 定义带约束的 schema、捕获 ValidationError 并提取字段级错误
3. 手写容错解析：剥代码块围栏、截取 JSON 主体、修复常见格式伤
4. 实现"校验失败 → 错误回传模型 → 自我修正"的重试循环，并设上限防死循环

## 4.1 为什么必须结构化

LLM 的输出本质是**一串字符**。你的下游程序需要的是"保证有 `category` 字段、值在枚举内、金额大于 0"的数据。两者之间的鸿沟，在 Java 里由编译器和 DTO 填平；在 Python + LLM 里，运行前没有任何东西替你把关——**不设防的结构化输出 = 把未校验的外部输入直接灌进业务逻辑**，这是老 Java 面试题"永远不信任外部输入"的 LLM 版本。

而且模型输出还有一个传统外部输入没有的麻烦：它**不稳定**。同一个 prompt，十次里九次吐合法 JSON、一次在前面加"好的："，这在生产里叫"周一早上必现故障"。

> ☕ Java 视角：传统接口的保障来自契约（WSDL/OpenAPI）+ 框架校验（Bean Validation）+ 反序列化器三件套。LLM 接口三者全无，全要你在应用层自己搭——下面三层防御就是这三件套的转世。

## 4.2 三层防御

| 层 | 手段 | 挡什么 | 局限 |
|---|---|---|---|
| API 层 | 传 `response_format` 请求 JSON 模式 / JSON Schema 约束输出（参数名与支持度以官方文档为准） | 从源头强制格式 | 各家/各兼容端点支持度不一，换供应商可能失效 |
| 约定层 | L03 的格式约定 + few-shot | 大部分格式跑偏 | 君子协定，无保证 |
| 校验层 | Pydantic 解析 + 容错 + 失败重试 | 一切漏网之鱼 | 需要写代码（本课主体） |

工程默认组合是**约定层 + 校验层**：不依赖任何平台的特殊参数，任何兼容端点都能用；API 层作为可选增强，有就开、没有不伤。这个"平台无关优先"的思路贯穿本轨道——阶段 3 谈框架锁定时你会再次遇到它。

> 🍿 彩蛋｜JSON 模式也有翻车现场：即使平台承诺"只输出 JSON"，也可能遇到空对象、字段齐全但全是空串、枚举外的"创意值"。所以行业共识是：**校验层永远不能省**——它不是不信任 JSON 模式，是不信任任何单一防线（想想你敢只靠防火墙不写鉴权吗）。

## 4.3 Pydantic：声明即校验

Pydantic 是 Python 的数据校验库（文档见 docs.pydantic.dev，v2 语法）：类定义即 schema，解析与校验一步完成：

```python
"""Pydantic 结构化输出最小示例：类即契约，解析即验收。依赖：uv add pydantic"""
from typing import Literal

from pydantic import BaseModel, Field, ValidationError


class Ticket(BaseModel):
    category: Literal["咨询", "投诉", "合作", "unknown"]      # 枚举：白名单
    priority: int = Field(ge=1, le=5, description="1 最低 5 最高")  # 数值范围
    summary: str = Field(min_length=5, max_length=100)        # 长度约束


def main() -> None:
    good = '{"category": "投诉", "priority": 4, "summary": "系统反复崩溃要求退款"}'
    bad = '{"category": "抱怨", "priority": 9, "summary": "崩"}'
    for raw in (good, bad):
        try:
            t = Ticket.model_validate_json(raw)     # 解析 + 校验，一步到位
            print("通过:", t.model_dump())           # 转回 dict 继续业务
        except ValidationError as e:
            print("拒绝:", [err["loc"] for err in e.errors()])  # 字段级错误定位


if __name__ == "__main__":
    main()
```

`ValidationError.errors()` 给出每个失败字段的位置与原因——这个信息别只写进日志，**它就是回传给模型的修复说明书**（4.5 节）。

> ☕ Java 视角：Pydantic = DTO + Bean Validation（`@NotNull`/`@Size`/`@Pattern`）+ Jackson 反序列化的三位一体，但声明全在一个类里，且校验失败抛出的异常自带字段级明细。写起来像 Lombok，管得像 Hibernate Validator。

## 4.4 容错解析：先洗再读

模型输出最常见的三种伤：markdown 围栏（```json ... ```）、前后混入解释文字、多余逗号。容错解析的职责是在 `json.loads` 之前尽量把伤修好：

```python
import json
import re


def tolerant_json_loads(text: str) -> dict:
    """尽力从模型的原始输出里抠出合法 JSON；修不好就抛 ValueError 交给上层重试。"""
    cleaned = text.strip()
    fence = re.search(r"```(?:json)?\s*(.+?)\s*```", cleaned, re.DOTALL)  # 剥围栏
    if fence:
        cleaned = fence.group(1)
    start, end = cleaned.find("{"), cleaned.rfind("}")                    # 截取首尾大括号
    if start == -1 or end == -1:
        raise ValueError("输出里找不到 JSON 对象")
    cleaned = cleaned[start:end + 1]
    cleaned = re.sub(r",\s*([}\]])", r"\1", cleaned)                      # 去尾逗号
    return json.loads(cleaned)                                            # 仍失败则抛 JSONDecodeError
```

写容错解析的纪律：**只修"格式伤"，不修"语义伤"**。缺字段、枚举外的值属于语义伤，交给 Pydantic 拒绝并触发重试——你手工"帮"模型补字段的那一刻，就是在静默生产脏数据。

## 4.5 自我修正循环：把错误说明书寄回给模型

容错+校验都失败时，杀手锏是把错误信息回传，让模型自己修：

```
第 1 次请求：prompt（含 schema）                → 模型输出（有伤）
第 2 次请求：历史 + "你的上一次输出无法通过校验，错误如下：
             category: 枚举外取值'抱怨'；priority: 9 超出 [1,5]
             请只输出修正后的 JSON"            → 模型输出（通常已合法）
```

这就是**自我修正循环**：多数格式问题一轮就能修好，但必须设重试上限（通常 2-3 次）——防止模型陷入"重复输出同一种坏格式"的死循环，把 token 烧成白噪音。这个"把错误结构化地喂回去"的模式是 Agent 开发的通用姿势：阶段 1 工具执行的错误返回、阶段 2 的评估反馈，全是它的变奏。

## 4.7 翻车形态速查表

把现场最常见的输出翻车与"归哪层处理"对齐（这张表建议存在手边，出事故时按行查找）：

| 翻车形态 | 归属 | 处理 |
|---|---|---|
| ```json 围栏包裹 | 格式伤 | 容错解析剥围栏 |
| 前后混"好的，以下是：" | 格式伤 | 截取首尾大括号 |
| 行尾/末字段多余逗号 | 格式伤 | 正则去尾逗号 |
| 键没加双引号 | 格式伤（高风险） | 谨慎正则修复，修不动就重试 |
| 缺字段 / 枚举外取值 / 越界数值 | 语义伤 | Pydantic 拒绝 → 错误回传重试 |
| 输出两段 JSON（正文+补充） | 结构伤 | 截取第一个完整对象；prompt 加"只输出一个对象" |
| 长文本把 JSON 撑爆 max_tokens | 资源伤 | 拆任务或限制生成长度，重试救不了 |

注意最后一行：有些问题重试也救不了，要在请求参数与任务设计层面解决——**先分类，再用药**，与阶段 2 检索质量课的"先诊断再下药"是同一种工程思维。

## 4.8 动手实验指引

跑 `code/L04_structured_output.py` 时按这个顺序实验（比"跑一遍看输出"有效十倍）：

1. 直接跑（mock 模式）：观察三份翻车样例分别被哪一层接住——围栏与尾逗号被容错解析修掉，越界的 priority 被 Pydantic 拒绝
2. 把 `tolerant_json_loads` 里剥围栏的正则注释掉，再跑：确认围栏样例现在落到哪一层被拦（它应该触发重试而不是崩溃）
3. 把 `MAX_RETRIES` 改成 0，把 mock 固定为越界样例：验证程序"必然终止"且退出码非 0
4. 有 key 的话设 `LLM_API_KEY` 跑真实模式，对比真实模型的翻车率（以及：把它输出的 JSON 故意改坏一个字段，看错误说明书长什么样）

实验 2 和 3 是关键：**防御体系的价值不在"都通过时"，而在"某一层被拆掉时系统仍不失控"**——这和你在 Java 里验证熔断器是一个测法。

## 练习

1. 为"旅游行程规划"设计 schema：嵌套（days 列表内含 places）、枚举（travel_mode）、数值范围（budget 下限）。
   提示：Pydantic 支持嵌套 BaseModel 与 `list[X]` 字段，先定义内层再定义外层。
2. 扩展 `tolerant_json_loads`：处理"键没加双引号"（如 `{category: "投诉"}`）。
   提示：可以用正则给裸键补引号；想想为什么这个修复有风险、什么情况下会修错。
3. 把自我修正循环的重试上限设为 1、mock 固定输出同一种坏格式，验证循环必然终止。
   提示：终止性由上限保证，与模型行为无关——这是它必须存在于代码而非 prompt 的原因。

## 小结与自测

- 问：三层防御各挡什么？答：API 层源头强制格式（依赖平台支持）、约定层靠 prompt 挡大部分跑偏、校验层用 Pydantic 兜住一切漏网之鱼。
- 问：为什么默认组合是约定+校验？答：不依赖特定平台的参数，任何兼容端点行为一致，可移植性优先。
- 问：容错解析为什么"只修格式不修语义"？答：手工补语义等于静默生产脏数据；语义错误应被拒绝并触发模型自修正。
- 问：自我修正循环为什么必须设上限？答：模型可能重复输出同种坏格式，上限保证程序必然终止。
- 问：ValidationError 的 errors() 有什么工程用途？答：字段级错误定位，直接作为回传模型的修复说明书。
