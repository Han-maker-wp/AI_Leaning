## 5.1 为什么 LLM 应用天然需要异步

一次 LLM 调用 = 几百毫秒到几十秒的**网络 IO + 服务端排队**。CPU 在这段时间里几乎空转。批量场景（总结 100 篇文档、并发评估 50 条问答）下，串行等待就是最大的浪费——这是纯 IO 密集问题，你在 Java 里用线程池或 CompletableFuture 早就解决过。

Python 的主流答案是 asyncio。先立好心智模型再写代码，一句话版：**asyncio = 单线程 + 事件循环 + 协作式调度**。

- 单线程：全程只有一个线程在跑你的 Python 代码，没有任何 CPU 并行
- 事件循环：一个调度器，维护一张"可运行任务"表
- 协作式：任务只在 `await` 处主动让出线程，事件循环趁机切换到别的任务——等待 IO 的任务让出的空隙，正好被别的任务的计算填上

> ☕ Java 视角：它不是 ThreadPoolExecutor（没有多线程抢占），而是 **Netty/Vert.x 的 EventLoop**——一个线程管成千上万个连接，靠"回调不阻塞"活着。又因为它原生 `async/await` 语法，写起来像 CompletableFuture 的 `thenCompose` 链但同步感更强。最大坑位也相同：**EventLoop 线程上绝不能跑阻塞调用**（`time.sleep`、同步 HTTP、大计算），一阻全阻；CPU 密集活要么进程池要么换同步方案。

## 5.2 最小可用集：五分钟上手

```python
"""asyncio 最小示例：对比串行等待与并发等待（纯标准库，离线可跑）"""
import asyncio
import time


async def fake_llm_call(name: str, seconds: float) -> str:
    await asyncio.sleep(seconds)     # 模拟 IO 等待：await 时让出线程
    return f"{name} 完成"


async def main() -> None:
    t0 = time.perf_counter()
    results = await asyncio.gather(   # 并发调度三个任务
        fake_llm_call("A", 1.0),
        fake_llm_call("B", 1.0),
        fake_llm_call("C", 1.0),
    )
    print(results, f"耗时 {time.perf_counter() - t0:.2f}s")   # ≈1s，不是 3s


if __name__ == "__main__":
    asyncio.run(main())               # 事件循环的入口：main 跑完循环关闭
```

三个最容易踩的概念坑：

1. **调用 async 函数不会执行它**——`fake_llm_call("A", 1.0)` 只是创建了协程对象，必须 `await` 它或交给 `gather`/事件循环才会跑。类比：造了个 Runnable，还没 submit。
2. `await` 不是"开新线程"，是"我愿意在这里让出，等结果好了再叫我"。
3. 并发收益来自**等待的叠加**，不是计算的并行——三个任务各自 sleep 1 秒，重叠后总耗时约 1 秒。

## 5.3 有限并发：gather + Semaphore

```python
"""批量任务 + 信号量限流骨架"""
import asyncio


async def worker(i: int, sem: asyncio.Semaphore) -> str:
    async with sem:                    # 拿不到名额就等待——并发天花板在这里
        return await fake_llm_call(f"任务{i}", 1.0)


async def main() -> None:
    sem = asyncio.Semaphore(5)         # 最多 5 路同时"在飞"
    results = await asyncio.gather(*(worker(i, sem) for i in range(20)))
    print(len(results), "个任务全部完成")


if __name__ == "__main__":
    asyncio.run(main())
```

**为什么不能无限并发**：LLM API 按分钟限流——RPM（每分钟请求数）与 TPM（每分钟 token 数）是平台配额的两把尺子。超限返回 HTTP 429，你的请求被拒之门外；更糟的是你自己的下游（向量库、数据库）也各有上限。`Semaphore` 就是你在客户端挂出的"闸门"：先跟配额协商一个安全并发度，再谈吞吐。经验起点是"配额的几分之一"再压测上调——具体配额以你所用平台的文档为准。

> ☕ Java 视角：Semaphore 就是 `java.util.concurrent.Semaphore` 的老熟人，连"限流先拿许可"的用法都一样；gather 相当于 `CompletableFuture.allOf(...).join()` 后收集结果，且 `gather` 保证结果顺序与参数顺序一致，不用你自己编号。

## 5.4 速率限制与指数退避重试

429 不是错误，是平台在说"排队，稍后再来"。标准应对是**指数退避（exponential backoff）**：第 n 次重试前等待 `base × 2^n` 秒，外加随机抖动（jitter）：

```python
import asyncio
import random


async def call_with_retry(task, max_retries: int = 4, base: float = 1.0):
    for attempt in range(max_retries + 1):
        try:
            return await task()
        except RateLimited:                       # 模拟的 429 异常类型
            if attempt == max_retries:
                raise                             # 重试额度用尽，如实上抛
            delay = base * (2 ** attempt) + random.uniform(0, 1)   # 1s,2s,4s,8s + 抖动
            await asyncio.sleep(delay)
```

**为什么要加抖动**：假设你的 50 个请求同时吃到 429，又都精确等 2 秒重试——它们会齐刷刷再次撞限流，永远齐步走、永远互相踩踏（这个现象叫重试风暴，是把故障放大的经典机制）。抖动把"齐步走"打散成"随机散布"，每次重试的实际压力减半再减半。

**哪些错误不该重试**：4xx 里的参数错误（400）、鉴权失败（401/403）是确定性失败，重试一万次结果相同，还烧配额——该立刻失败并报给人。可重试的典型是 429（限流）、5xx（服务端抖动）、网络超时。**"可重试性"要显式分类，不能一把梭 try/except。**

> 🍿 彩蛋｜这套"退避+抖动"不是 LLM 时代的发明——它是分布式系统的祖传手艺，数据库重连、消息队列消费、微服务熔断里全是它。LLM API 只是最新一个"不可靠外部依赖"。你带着分布式经验进 Agent 开发，这属于降维打击区。

## 5.6 调参速查与自检清单

批量调用的四个旋钮，起点值与调整方向：

| 参数 | 起点 | 往哪调 |
|---|---|---|
| 并发度（Semaphore） | 3-5 | 压测观察 429 率：出现就降，稳定可缓升 |
| max_retries | 3-4 | 长任务可加大，实时交互场景减小（快速失败） |
| 退避基数 base | 0.5-1s | 平台限流严格则加大（等更久再试） |
| 批大小（任务数） | 视任务 | 先小批验证正确性，再放量 |

上线前的自检三问：① 并发度是谁定的——拍脑袋还是压测？② 429 的退避带没带抖动？③ 部分失败时，结果里能不能看清谁失败、为什么（而不是整批报废或静默丢结果）？第三问最常被漏：`gather(return_exceptions=True)` 只是兜住了不崩，失败清单的汇报与补偿是你要自己写的。

## 5.7 为什么不用线程池（以及什么时候该用）

Java 直觉会问：线程池 + 阻塞 HTTP 不也能并发吗？能，但 Python 有个著名约束——**GIL（全局解释器锁）**：同一时刻只有一个线程执行 Python 字节码。线程池在 Python 里对 IO 密集任务同样有效（等待时释放 GIL），但相比 asyncio 有三个劣势：

1. **线程开销**：每个线程 MB 级栈内存 + 切换成本；协程只是个对象，千级并发毫无压力
2. **竞态风险**：多线程共享状态要加锁，asyncio 单线程内 `await` 之间的代码天然无抢占，心智负担小一个量级
3. **生态**：现代 LLM/HTTP 客户端都提供 async 接口，主流玩法在这边

什么时候反而用线程/进程：CPU 密集任务（本地向量化批处理、文档解析）用进程池（绕开 GIL）；给同步工具套超时（阶段 1 L02 的手法）用线程池。**IO 并发 asyncio、CPU 并行进程池、同步转异步线程池**——三句话就是你需要的全部选型规则。

## 小结与自测

- 问：asyncio 为什么快？答：不是并行计算，是单线程事件循环让 IO 等待互相重叠，等待期线程去跑别的任务。
- 问：EventLoop 线程上最忌讳什么？答：阻塞调用（同步 IO、sleep、大计算），一阻全阻。
- 问：Semaphore 为什么不可省？答：平台有 RPM/TPM 限流、下游有容量上限，信号量是客户端闸门，防 429 与自我 DDoS。
- 问：退避为什么要加 jitter？答：防止并发请求齐步走、同步撞限流形成重试风暴。
- 问：哪些错误不重试？答：确定性失败（参数错、鉴权错等 4xx），重试无效且浪费配额，应立即报错。
