# 第 2 课：工具设计学——给模型用的 API 设计

> 🎬 开场钩子：同一个"查天气"功能，description 从「查询天气」改成「查询指定中国城市的当前天气，返回摄氏温度；不支持海外城市」——模型调用准确率立刻不同，连"纽约天气吗"这种越界请求都会被正确拒绝。工具接口你还是十年前那套手艺，但调用方从人类前端换成了模型——**所有设计决策都要按新用户的认知方式重新过一遍**。

⏱ 建议学时：1.5 小时

## 本课目标

1. 按模型的使用方式设计参数与描述（枚举、单位、时区、必填最小化）
2. 实现结构化的错误返回：工具异常转文本、模型可自纠
3. 解释幂等性在 Agent 场景为什么比传统 API 更关键
4. 给工具挂上超时与日志，形成"可观测的最小习惯"

## 2.1 模型怎么"选"工具：匹配的是语义

模型选工具没有魔法：它把请求语义与每个工具的 `name + description + 参数描述` 做匹配，选最贴切的。推论很直接——**工具文档质量 = 调用准确率**。四条设计军规：

1. **一个工具做一件事**（SRP 在工具界复活）：`manage_file(action: read|write|delete)` 这种"万能参数"工具，模型调对的概率远低于三个独立工具。粒度越单纯，语义匹配越清晰
2. **枚举优于自由文本**：`op: "add|sub|mul|div"` 好过让模型填运算符字符串；能被 schema 约束的，绝不靠模型自觉
3. **把单位与时区写进描述**："金额单位为分"、"时间为 UTC+8 的 ISO 格式"——不写，模型就会按训练数据里最频繁的约定自由发挥
4. **必填参数最小化**：每个必填参数都是一个必须推理正确的点。有合理默认值的参数，声明为可选并写明默认语义

> ☕ Java 视角：这就是你写了十年的接口设计，只是消费者从"会看文档的人"变成"只看 description 的模型"。人类程序员会去读上下文、猜你的意图、踩坑后看报错；模型只看你给的几十个词。所以工具描述的认真程度，要按"这段文字是唯一的接口文档"来要求。

## 2.2 错误返回：把工具异常翻译给模型

新手最本能的写法是工具里 `raise`。但异常一抛，你的 Agent 循环就崩了——而其实模型完全有能力**读懂错误并自纠**：参数填错 City 名？它重试。城市不支持？它向用户澄清。前提是你把错误翻译成它能消费的文本：

```python
def tool_error(code: str, message: str, hint: str = "") -> str:
    """把工具错误包装成结构化文本——错误也是给模型的输出，不是给栈的。"""
    return json.dumps({"ok": False, "error": code, "message": message, "hint": hint},
                      ensure_ascii=False)


def get_weather(city: str) -> str:
    if city not in CITY_DB:
        return tool_error("CITY_NOT_FOUND", f"不支持的城市: {city}",
                          hint="仅支持中国城市，请确认城市名或向用户澄清")
    return json.dumps({"ok": True, "temp_c": CITY_DB[city], "city": city},
                      ensure_ascii=False)
```

设计要点：

- **可自纠错误 vs 不可自纠错误分开**：参数错、城市不存在（hint 教模型怎么办）；外部服务挂了（模型只能如实转告用户）
- **hint 字段是点睛之笔**：告诉模型"下一步怎么办"，而不只是"出错了"——这直接决定它重试还是求助
- **真正的异常（网络炸了、bug）在 dispatch 层兜底**：catch 住后同样转成 error 文本回填，循环不死

这套"错误即输出"的哲学和给人类的 API 设计不同：人类看 500 会打电话给你；模型看结构化错误会自己改参数再试——前提是你给了它能读懂的错误。

## 2.3 幂等：模型会重试，用户会重发

幂等 = 同一操作执行多次，效果与执行一次相同。Agent 场景把它的重要性放大了数倍，因为**重复执行的触发源变多了**：

- 模型没读懂结果，决定"再调一次"
- 你的重试逻辑（L05 的指数退避）在超时后重发
- 用户说"再发一次"时，模型可能把上次的"写邮件"工具又执行了一遍

工程对策按副作用等级递进：

| 副作用 | 策略 |
|---|---|
| 读操作（查询/搜索） | 天然幂等，随便重试 |
| 写操作但可覆盖（写文件、更新状态） | 以"最终状态"语义设计：`write_file(path, content)` 幂等；`append_file` 不幂等 |
| 不可逆动作（发邮件、支付、删除） | 幂等键（请求带唯一 id，执行前去重）+ **人工确认**（human-in-the-loop） |

> ☕ Java 视角：POST 重复提交、支付接口的幂等 token、消息队列的 exactly-once 语义——同一门课的新学期。区别是：传统场景重复的来源是"网络与用户"，Agent 场景还要加上"模型的自主决策"，它真的会自己决定再调一次。

human-in-the-loop 现在只需最简版：给工具打 `dangerous` 标签，执行前 `input("确认执行? [y/N]")`。阶段 3 LangGraph 会给出带中断/恢复的正式机制。

## 2.4 超时与日志：从第一天就有的两个习惯

**超时**：模型等你的工具，用户等模型——链条上任何一环卡死，整条链死。每个工具（尤其涉及网络/大文件）必须有超时；超时发生时同样返回 error 文本（"外部服务超时，请建议用户稍后再试"），而不是让第 8 秒变成永远。标准库够用：`concurrent.futures.ThreadPoolExecutor` 包住同步调用加 `future.result(timeout=...)`，或网络库自带的 timeout 参数。

**日志**：Agent 的调用链是"模型 ↔ 工具"多跳的，出问题时没有日志等于盲调。最小习惯——每次工具调用记四元组：

```python
import logging
import time

log = logging.getLogger("agent.tools")   # 阶段 4 会升级为结构化 tracing，习惯先落地

def safe_call(name: str, func, args: dict) -> str:
    t0 = time.perf_counter()
    try:
        result = func(**args)
        status = "ok"
        return result if isinstance(result, str) else json.dumps(result, ensure_ascii=False)
    except Exception as e:                       # 兜底：任何异常都转文本，循环不死
        status = "error"
        return tool_error("TOOL_CRASH", f"{type(e).__name__}: {e}")
    finally:
        log.info("tool=%s status=%s cost=%.0fms args=%s", name, status,
                 (time.perf_counter() - t0) * 1000, list(args.keys()))
```

注意 finally 的写法：**成败都要记**，成本统计（cost）以后就是你的成本看板数据源；`args.keys()` 记参数名而不记值——工具参数里可能有用户隐私，脱敏习惯同样从第一天开始。

> 🍿 彩蛋｜行业黑话里这叫 tool observability（工具可观测）：一个生产 Agent 每次回答平均要跑几十次模型/工具调用，没有结构化日志与调用链追踪，线上排障全靠猜。阶段 4 L01 整课讲这个，但习惯是现在养的。

## 2.5 反例与正例：同一个工具的两种写法

```python
# ❌ 反例：模型视角的"三无"工具——何时用不知道、参数单位没说、错了不知道怎么救
BAD_WEATHER_TOOL = {
    "type": "function",
    "function": {
        "name": "tool_1",
        "description": "天气相关功能",
        "parameters": {"type": "object", "properties": {
            "s": {"type": "string"},          # s 是什么？城市？城市id？
            "opt": {"type": "string"},         # 自由字符串=枚举失控
        }, "required": ["s", "opt"]},
    },
}

# ✅ 正例：name 语义化、description 讲清边界与单位、枚举收口、必填最小化
GOOD_WEATHER_TOOL = {
    "type": "function",
    "function": {
        "name": "get_current_weather",
        "description": "查询指定城市当前天气。仅支持中国城市；温度为摄氏度；只查当前，不查预报。",
        "parameters": {"type": "object", "properties": {
            "city": {"type": "string", "description": "城市中文名，如「杭州」"},
            "unit": {"type": "string", "enum": ["C"],
                     "description": "温度单位，当前仅支持摄氏度"},
        }, "required": ["city"]},
    },
}
```

对照出四条差距：名字（`tool_1` vs 动词短语）、描述（"相关功能" vs 边界+单位+时态）、参数（神秘单字母 vs 自解释+枚举）、必填（两个 vs 一个）。工具评审时把这段反例贴出来当镜子——**schema 是给模型的文档，不是给编译器的占位**。

## 2.6 工具上线前检查清单

- [ ] description 说清：何时用 / 何时不适用 / 单位与时区
- [ ] 参数全部自解释，能枚举的都枚举，必填最小化
- [ ] 每种可预期错误都有结构化返回（含 hint），真异常在 dispatch 层兜底
- [ ] 有超时；超时返回 error 文本而非挂死
- [ ] 副作用分级完成：read / write / dangerous，dangerous 已接确认
- [ ] 日志四元组（名/状态/耗时/参数名）已接入

## 练习

1. 下面三个"烂 schema"各改写成合格版：`{"name": "do_stuff", "description": "做事情"}`、带 5 个必填参数的搜索工具、用自由字符串传日期的工具。
   提示：分别对应描述空泛、必填过多、缺格式约定三个坑。
2. 给 L01 的 `get_weather` 加上完整错误体系：CITY_NOT_FOUND（可自纠，带 hint）、SERVICE_TIMEOUT（不可自纠）两种，并用 mock 验证模型能读懂 hint 后换正确的城市重试。
   提示：mock 按回填消息里的 error code 分支即可。
3. 实现 `safe_call` 的超时版：用 ThreadPoolExecutor + future.result(timeout)，超时返回 error 文本。
   提示：线程池里的任务超时后仍在跑，理解"结果等不及"与"任务被杀死"的区别即可，深究留到 L05。

## 小结与自测

- 问：工具描述按什么标准写？答：按"这是模型唯一能读到的接口文档"——何时用、范围、单位、时区都要写清。
- 问：工具出错为什么不抛异常？答：异常炸循环；结构化错误文本 + hint 能让模型自纠或如实转告，错误也是输出。
- 问：Agent 场景幂等为什么更关键？答：重复执行的来源多了"模型自主重试"与"用户重发"，不可逆动作要幂等键+人工确认。
- 问：超时后返回什么？答：error 文本（告知模型外部服务超时），保证链条不死、模型能向用户解释。
- 问：日志最小四元组？答：工具名、状态、耗时、参数名（脱敏不记值）。
