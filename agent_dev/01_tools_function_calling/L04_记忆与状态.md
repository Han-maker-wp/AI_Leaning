# 第 4 课：记忆与状态——模型其实每次都失忆

> 🎬 开场钩子：一个反直觉的真相：模型没有记忆。你感觉它"记得"三小时前的对话，是因为每一次请求，你的客户端都把全部历史重新发了一遍——并按 token 付费。所以长对话的账单是平方级增长的：第 10 轮的一句"好的"，要为前 9 轮全额买单。今天我们管好这笔账，顺便让 Agent 拥有跨越重启的真记忆。

⏱ 建议学时：2 小时（讲义内嵌 SQLite 示例离线可跑，建议亲手执行）

## 本课目标

1. 算清多轮对话的成本账（为什么是平方级），说清上下文窗口的两难
2. 会写滑窗截断与摘要压缩两种窗口管理策略，并知道各自的牺牲
3. 用 SQLite（标准库 sqlite3）实现会话持久化与恢复
4. 理解"状态外置"：Agent 的变量放存储，不指望模型背住

## 4.1 无状态的代价：滚动雪球的账单

回顾 L02 的事实：API 无状态，多轮 = 每轮全量重发。算一笔账（数字为示意，单价以平台为准）：假设每轮新增 1000 token 的历史，第 n 轮的输入 ≈ 前 n-1 轮全部 + 本轮输入。累计输入成本 ≈ 1000 × (1+2+…+n) ≈ **500·n²** 量级——第 20 轮会话的单轮成本是第 2 轮的约 10 倍。再叠加上限约束：上下文窗口（模型一次能"看见"的 token 上限）迟早被填满，超限直接报错。

所以记忆管理的本质是一道工程权衡题：**窗口里放什么、放多少**。两条基本路线如下。

## 4.2 窗口管理：滑窗与摘要压缩

**策略一：滑动窗口（简单粗暴）**。保留 system + 最近 k 轮，老消息直接丢弃：

```python
def sliding_window(messages: list[dict], keep_rounds: int = 6) -> list[dict]:
    """保留 system + 最近 keep_rounds 轮（一轮 = user+assistant 两条）。"""
    system = [m for m in messages if m["role"] == "system"]
    rest = [m for m in messages if m["role"] != "system"]
    return system + rest[-keep_rounds * 2:]
```

优点：一行逻辑、token 可控。牺牲：老信息**硬丢失**——用户第 2 轮说过的"预算 5000 以内"，滑出窗口后模型彻底失忆。适合闲聊型助手，不适合任务型 Agent。

**策略二：摘要压缩（有损但保要点）**。老消息不删光，而是请模型压缩成一段摘要放回上下文：

```
触发条件：估算 token 超过阈值（简化实现用 len(text) 代替精确计数）
压缩动作：messages = [system + 旧对话摘要] + 最近几轮原文
摘要 prompt：把以下对话压缩成要点（用户目标、已确认的约束、关键决定、
             未决问题），不要丢失数字与偏好
```

牺牲的是细节（逐字引用没了），换来的是**要点跨窗口存活**。注意摘要本身也是一次模型调用——有成本、有延迟，所以按阈值触发而不是每轮压缩；且摘要 prompt 里"不要丢数字与偏好"这类叮嘱很关键，摘要器最容易丢的恰恰是这些。

> ☕ Java 视角：这就是缓存淘汰策略的故事——滑窗 ≈ FIFO/LRU 直接丢弃，摘要 ≈ 把冷数据降级归档（明细转报表）。没有"正确答案"，只有"你的业务丢了什么会疼"。

> 🍿 彩蛋｜Karpathy 2023 年的 "LLM OS" 设想把这套关系讲得最透：上下文窗口是内存（RAM），装不下的是硬盘。内存贵而快、硬盘便宜而持久——摘要压缩是"换页"，检索（下阶段 RAG）是"按需从硬盘调页进内存"。你马上要在阶段 2 写的 RAG，在他的图里就是那块硬盘。

## 4.3 持久化：SQLite 存会话

内存里的 messages 一重启就没了。生产级的 Agent 需要"会话"作为一等公民：可保存、可恢复、可列表。标准库 sqlite3 零依赖起步：

```python
"""会话持久化最小实现：建表 / 追加消息 / 加载恢复。纯标准库，离线可跑。"""
import json
import sqlite3
from datetime import datetime, timezone

DB_PATH = "agent_memory.db"


def init_db(conn: sqlite3.Connection) -> None:
    conn.execute("""CREATE TABLE IF NOT EXISTS sessions (
        session_id TEXT NOT NULL,
        seq        INTEGER NOT NULL,          -- 消息序号：恢复时按它排序
        role       TEXT NOT NULL,
        content    TEXT NOT NULL,
        created_at TEXT NOT NULL,
        PRIMARY KEY (session_id, seq))""")


def append_message(conn: sqlite3.Connection, sid: str, seq: int, role: str, content: str) -> None:
    conn.execute("INSERT INTO sessions VALUES (?,?,?,?,?)",
                 (sid, seq, role, content, datetime.now(timezone.utc).isoformat()))
    conn.commit()


def load_messages(conn: sqlite3.Connection, sid: str) -> list[dict]:
    rows = conn.execute(
        "SELECT role, content FROM sessions WHERE session_id=? ORDER BY seq", (sid,)
    ).fetchall()
    return [{"role": r, "content": c} for r, c in rows]


if __name__ == "__main__":
    conn = sqlite3.connect(DB_PATH)
    init_db(conn)
    sid = "demo-001"
    append_message(conn, sid, 0, "system", "你是简洁助手")
    append_message(conn, sid, 1, "user", "记住我的预算是 5000")
    append_message(conn, sid, 2, "assistant", "好的，已记下预算 5000。")
    print("重启后恢复:", json.dumps(load_messages(conn, sid), ensure_ascii=False, indent=2))
```

恢复 = `load_messages` 重建 messages 列表再进循环，Agent 重启不失忆。JSON 文件也能干这事（更简单），但 SQLite 赢在三件事：多会话查询（`WHERE session_id=?` 天然按会话隔离）、并发写安全、增量追加不用整文件重写。会话多了以后，再加一张 `session_meta` 表（标题/摘要/更新时间）做会话列表——这就是你 checkpoint 要做的扩展。

> ☕ Java 视角：SQLite ≈ 嵌入式 H2：单文件数据库、零部署、进程内访问，中小 Agent 的会话存储绰绰有余；真要多实例部署再换 PostgreSQL，接口层不变。

## 4.4 状态外置：别让模型"背"变量

最后一条原则，也是最容易被忽视的：**Agent 的任务状态（待办清单、中间结果、用户约束）应该存在代码里的结构化存储中，而不是散落在对话文本里指望模型"记得"**。

原因：模型对上下文的"记忆"是概率性的——第 2 轮说的预算，第 15 轮它可能记得、可能模糊、可能张冠李戴；而一个 `constraints = {"budget": 5000}` 的字典永远精确。工程做法：结构化状态存 DB/内存，每轮调用时**把状态序列化注入 prompt**（"当前已知约束：预算 5000…"）——模型读到的永远是新鲜事实，而不是靠"回忆"。

这同时是解耦：换模型、清窗口、摘要压缩，都不动状态本身。阶段 3 LangGraph 的核心概念 `State`（状态对象在图节点间流转），就是这条原则的框架化。

## 4.5 记忆策略决策表

按场景选策略，别上来就摘要（摘要是最贵的方案）：

| 场景 | 推荐策略 | 理由 |
|---|---|---|
| 闲聊/短任务助手 | 滑窗 k=6-10 轮 | 实现零成本，丢老信息无伤大雅 |
| 任务型 Agent（约束要长期记住） | 滑窗 + 状态外置（约束进 DB 每轮注入） | 关键事实不靠模型记忆，靠代码保证 |
| 长咨询/顾问对话 | 滑窗 + 阈值触发摘要 | 跨窗口保要点，成本可控 |
| 客服工单（要审计） | 全量持久化不删 + 检索按需调取 | 合规优先；老对话进知识库而非留在窗口 |

token 估算的工程简化：精确计数要分词器，日常用 `len(text)` 除以经验系数（中文 1 字符 ≈ 1~2 token，取保守值 1.5）估算触发阈值就够了——估算只用于"什么时候该压缩"的决策，计费仍看 usage（L02 的纪律）。

```python
def est_tokens(text: str) -> int:
    """粗估 token 数：只用于压缩触发等内部决策，不用于计费。"""
    return int(len(text) * 1.5)
```

> ☕ Java 视角：这张决策表就是你熟悉的"缓存策略选型"——本地缓存、Redis、CDN 各有适用面，没有万能解。记忆分层（窗口/摘要/外部存储）本质上就是 L1/L2/L3：越近越快越贵、容量越小。

## 4.6 持久化方案对比与迁移路径

| 方案 | 适用 | 上限 |
|---|---|---|
| 内存 list | 原型、单次会话 | 进程退出即失忆 |
| JSON 文件 | 单用户小工具、随手存 | 多会话并发写会互相覆盖 |
| SQLite | 单机多会话（**本课推荐**） | 单机写入吞吐 |
| PostgreSQL 等 | 多实例部署、生产 | 运维成本随之而来 |

迁移路径刻意保持简单：把"读消息/写消息"收敛成 `load_messages(sid)` 与 `append_message(sid, msg)` 两个函数，业务循环只认函数不认存储——换库时改函数体，循环零改动。这个"存储边界收敛成接口"的手法，和你在 Java 里用 DAO 隔离持久化是同一招。

checkpoint 提示：会话表加 `session_meta`（标题/创建时间/最后活跃时间）后，"列出历史会话、继续上次对话"就是两条 SQL 的事——体验立刻从玩具升到产品雏形。

## 小结与自测

- 问：多轮成本为什么平方级？答：每轮重发全部历史，第 n 轮输入 ≈ 前n-1轮总和，累计是 n² 量级。
- 问：滑窗与摘要各自的牺牲？答：滑窗硬丢老信息、实现最简单；摘要保要点但丢细节，且压缩本身有成本与失真风险。
- 问：SQLite 相比 JSON 文件赢在哪？答：多会话隔离查询、并发写安全、增量追加；JSON 仅适合单会话原型。
- 问：为什么状态要外置？答：模型记忆是概率性的，结构化存储是精确的；状态外置还能随轮次新鲜注入，不怕窗口清理。
- 问：Karpathy 的 LLM OS 里 RAG 对应什么？答：硬盘——上下文（内存）装不下的知识，按需检索调页进来。
