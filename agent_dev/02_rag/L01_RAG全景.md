# 第 1 课：RAG 全景——给模型外挂一个书架

> 🎬 开场钩子：问一个内部部署的模型"我们公司新的报销制度是什么"，它一本正经地编了一套流程，条款齐全、语气权威，全是编的。这不是故障，是概率生成器的本性：它只负责给出"最像答案的话"。RAG 的思路朴素到惊人——别让它闭卷考试，把相关资料摊开在它面前。这五课我们就造这个"摊资料"的系统。

⏱ 建议学时：1.5 小时

## 本课目标

1. 说清 RAG 要解决的三个痛点：知识截止、私有数据、幻觉与不可溯源
2. 白板画出离线索引与在线问答两条链路，标出每步输入输出
3. 能做 RAG vs 微调的选型判断（并知道何时两者叠加）
4. 建立"检索质量决定上限"的全局观，为后面四课立好地图

## 1.1 三个痛点，一个对策

- **知识截止**：模型的"世界知识"冻结在训练数据的时间边界上，之后发生的事它一无所知——问就是编
- **私有数据**：你的内部文档、个人笔记、产品手册，模型训练时没见过，永远答不了
- **幻觉与不可溯源**：生成式模型的输出没有"出处"概念，错得再离谱也一样自信；用户无法验证，你无法定位

RAG（Retrieval-Augmented Generation，检索增强生成）的对策：**先检索，后生成**——把与问题相关的资料从你的知识库里捞出来，塞进上下文，再让模型"参考资料作答"。三个痛点同时缓解：知识可以实时更新（换文档就行）、私有数据可检索、答案有出处可引用。

> ☕ Java 视角：这套"把事实从代码挪到数据"的智慧你在 Java 世界用过无数遍——把魔法数字抽成配置、把规则抽成数据库、把逻辑抽成策略表。RAG 做的是同一件事：模型的"参数"是编译期写死的常量（训练出来的权重），上下文是运行时传入的请求参数。**易变的事实放运行时，稳定的能力放参数**。

## 1.2 全景图：两条链路

RAG 系统永远是两条链路，分开理解就不会乱：

```
【离线 · 索引链路】（跑一次/文档变更时跑）
  原始文档 → 加载解析 → 清洗 → 分块 chunking → embedding 向量化
       → 存入向量库（向量 + 原文 + 元数据）

【在线 · 问答链路】（每次提问跑）
  用户问题 → embedding → 向量库检索 top-k 个相关 chunk
       → 组装 prompt（问题 + 检索到的资料 + 引用指令）
       → LLM 生成带引用的回答
```

几个"为什么"先埋在这里，后面各课逐一展开：

- 为什么要**分块**（L02）：检索的最小单位不是整篇文档——粒度决定检索精度与上下文预算
- 为什么要 **embedding**（L03）：让"怎么退款"能匹配到"退货流程"——语义搜索而不是关键词匹配
- 为什么检索之后还要**混合与精排**（L04）：向量检索有盲区，单一通道总会漏
- 为什么要**评估**（L05）：不度量，你就永远在"感觉变准了"里打转

> 🍿 彩蛋｜行业黑话："RAG 不生产知识，它只是知识的搬运工"。另一句更狠："垃圾进，垃圾出"——索引链路的文档质量与分块质量，直接封顶问答链路的一切努力。所以本阶段一半的篇幅花在离线侧。

## 1.3 RAG vs 微调：本轨道与主线的交汇点

你同时在学两条轨道，这里正好把两个工具放上天平：

| 维度 | RAG | 微调 |
|---|---|---|
| 注入**知识**（事实、文档、时效数据） | ✅ 强项：换文档即更新 | ❌ 弱项：知识混进权重，更新一次训一次 |
| 改变**行为**（风格、格式、领域话术） | 一般：靠 prompt 约定，不稳定 | ✅ 强项：直接改变输出的分布 |
| 可溯源 | ✅ 答案可引用出处 | ❌ 无法指出"这条知识从哪来" |
| 成本与周期 | 低：建索引即可 | 高：数据构建 + 训练 + 评估（主线阶段 5 的全部内容） |
| 幻觉控制 | 检索质量好则显著缓解 | 不直接解决，甚至可能强化自信的错误 |

选型口诀：**知识问题用 RAG，行为问题用微调，两者不冲突**。"客服必须用三段式格式回复"是行为问题（微调）；"客服要答对最新的退款政策"是知识问题（RAG）；生产级的领域客服往往是 RAG + 微调双管齐下。主线阶段 5 会把微调全流程教给你，届时你是极少数两条腿都踩过的学员——选型判断会非常扎实。

别忘了第三选项：**很多问题直接 prompt 就够**。通用知识问答、文本改写、代码解释——模型的预训练知识 + 一个好 prompt 足以应付，上 RAG 是杀鸡用牛刀（还引入了维护成本）。判断顺序永远是：先问"模型本来就会吗"（直接 prompt），再问"它缺的是知识还是行为"（RAG / 微调）。**技术选型从"什么都不加"开始论证，而不是从"什么最流行"开始。**

> ☕ Java 视角：又是一个老朋友结构——RAG vs 微调 ≈ **运行时配置 vs 编译期常量**。改配置要重启吗？不用；改常量要重新构建部署。频繁变化的东西永远应该放"配置侧"。

## 1.4 从最小可用到生产级的路标

一个下午就能搭出的最小 RAG（L02+L03 的知识已够）：50 个 chunk、numpy 暴力扫、prompt 拼接。但生产级要回答更多问题：文档每天变怎么办（增量更新）、检索不准怎么办（混合+rerank）、怎么证明它比上一版好（评估集）、答案错了怎么定位（引用+tracing）。本阶段后四课就是这条升级路线，checkpoint 会带你走完一遍完整流程。

最后立一个贯穿始终的判断：**先测检索，再测生成**。检索没命中，生成再好也是无米之炊；而且检索指标（hit rate）便宜可复跑，生成评估又贵又主观——诊断永远从上游开始。

动手顺序（本阶段的实操节奏，每步以上一步能跑为前提）：

1. 学完 L02：拿自己的文档跑通分块 demo，肉眼看块形态
2. 学完 L03：MiniVectorStore + 真实 embedding 建索引，命令行问答跑通
3. 学完 L04：按评估信号决定加混合检索还是阈值过滤（不强求全上）
4. 学完 L05：建评估集回头看第 3 步的改动值不值，然后做 checkpoint

RAG 是一个系统而不是一招——按节奏搭，每一步都有可运行的东西在手。

## 1.5 RAG 的三种形态：从朴素到模块化

行业里常见的分期说法（不必背，用来给方案定位）：

- **朴素 RAG（Naive RAG）**：L02+L03 教的那条链路——分块、向量检索、拼接生成。一下午能搭完，覆盖 60 分场景
- **进阶 RAG（Advanced RAG）**：在朴素版两端加工程——索引侧优化分块与元数据，检索侧加混合检索、rerank、查询改写（L04 全课）。多数生产系统停在这一档
- **模块化 RAG（Modular RAG）**：把各环节拆成可替换模块自由编排——检索结果送另一个模型改写再生成、多路召回路由、RAG 与微调组合。阶段 3 的框架思想会与之呼应

判断你需要的档位：先用朴素版跑通并建评估集（L05），指标告诉你哪里疼再升级——**按评估升级，不按论文升级**。

> ☕ Java 视角：这就是架构演化的老剧本：单体（朴素）→ 加缓存与中间件（进阶）→ 服务化拆分（模块化）。没有一步到位的微服务，也没有一步到位的模块化 RAG；过早拆分是同一种病。

## 1.6 常见误区清单

| 误区 | 真相 |
|---|---|
| "RAG 能让模型变聪明" | RAG 只提供事实；推理能力仍取决于模型本身 |
| "把全部文档塞进长上下文就行了" | 上下文越长注意力越稀释、成本越高、且无检索定位——长窗口不替代检索，两者互补 |
| "检索不命中就调大 k" | 先查分块与 query 侧（L04），盲目调 k 只是往窗口里倒噪声 |
| "有了 RAG 就不会幻觉" | 检索到错误/不相关资料时照样编；忠实度要靠评估盯着（L05） |
| "文档丢进去就行，不用清洗" | 页眉页脚、目录、乱码全进了索引——垃圾进垃圾出 |
| "RAG 做完就不用微调了"（或反之） | 知识与行为是两个正交问题，按需组合 |
| "答案不好就换更强的生成模型" | 检索没命中时，换模型只是更流畅地胡说 |
| "评估以后再说" | 没有基线数字，所有改动都无从判断好坏 |

最后强调一遍全阶段的地图感：**离线侧（分块/元数据）决定上限，在线侧（检索/改写）逼近上限，评估侧告诉你差距在哪**。三句话就是后面四课的目录。

## 1.7 组装进 prompt 的样子

在线链路最后一步"组装 prompt"值得展开看一眼——它是 L03 输出格式约定的老手艺换了个战场：

```
[system]
你是知识库助手。只根据「资料」回答问题；资料不足以回答时明确说
"知识库中未找到相关内容"，禁止编造。每个事实性结论后标注 [资料编号]。

[user]
【资料】
[1]（来源：refund_policy.md · 售后>退款流程）退款将在 3-5 个工作日原路返回……
[2]（来源：pricing.md · 企业版）企业版按席位计费……
[3]（来源：faq.md · 退款）虚拟商品退款需扣除已使用部分……

【问题】
个人版买了三个月能退多少钱？
```

注意三个设计：资料带编号与来源（引用标注的前提）、"不足以回答就说没有"（空结果纪律的 prompt 侧）、"禁止编造"（忠实度的约定侧）。还有个隐藏细节：检索到了三条但只有 [1][3] 与问题相关——**prompt 里的"只根据资料"挡不住资料本身不相关**，这正是 L04 检索质量要解决的事。

自问自答一题：什么时候 RAG 也救不了？① 资料本身互相矛盾（治理问题，不是检索问题）；② 任务需要的是推理能力而非事实（换更强的模型）；③ 检索持续为零（文档覆盖缺口，先补库再调参数）。**先分类，再下药**的思维从此贯穿到阶段 4。

## 练习

1. 给你身边的三个真实场景做选型：① 团队 wiki 问答 ② 让周报永远用固定五段式写 ③ 教模型讲你们行业的黑话。各选 RAG/微调/直接 prompt，写一句理由。
   提示：问自己"我要注入的是事实还是行为"。
2. 估算题：一份 40 页的中文 PDF 约多少 token（按经验值估），全塞上下文和分块检索各有什么问题？
   提示：上下文窗口、成本、注意力稀释三个角度；经验值可设汉字≈1.5 token 量级做粗估，精确值以分词器为准。
3. 画出你所在团队知识的 RAG 数据流图（离线/在线两条链路），标出你认为最容易掉链子的环节。
   提示：常见答案是文档格式混乱（加载）与问题口语化（检索 query 侧），后面两课会分别应对。

## 小结与自测

- 问：RAG 解决哪三个痛点？答：知识截止、私有数据不可见、幻觉不可溯源——靠"先检索后生成 + 引用"。
- 问：离线索引链路的步骤？答：加载→清洗→分块→embedding→向量库（带元数据）。
- 问：在线问答链路的步骤？答：问题 embedding→top-k 检索→prompt 组装→生成（带引用）。
- 问：RAG vs 微调的一句话口诀？答：知识问题 RAG、行为问题微调、生产常叠加。
- 问：为什么先测检索再测生成？答：检索是上游，未命中则生成无米下锅；且检索指标便宜、可复跑、更客观。
