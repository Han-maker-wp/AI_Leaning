# 第 2 课：文档分块——RAG 里最便宜的调优旋钮

> 🎬 开场钩子：两个团队，同样的模型、同样的文档做知识库问答，一个能用一个翻车。排查下来差异只有一个：一个按 512 token 整齐切块（把表格从中间腰斩、把"该政策适用于"和它指代的主语切进两个块），另一个按标题与句子边界递归切。分块没有算法光环，却是**投入产出比最高**的 RAG 调优项——改它不要 GPU，只要想清楚。

⏱ 建议学时：2 小时（`code/L02_chunk_demo.py` 离线可跑，务必亲手改参数）

## 本课目标

1. 说清为什么必须分块：语义密度、检索粒度、上下文预算三个理由
2. 掌握固定长度 / 递归字符 / 语义三种分块策略与各自的适用面
3. 理解 chunk 大小与 overlap 的权衡，知道从哪里起步、往哪个方向调
4. 从第一天就给 chunk 配好元数据，说清它对过滤/引用/增量的决定性作用

## 2.1 为什么检索的最小单位是 chunk

朴素方案：整篇文档算一个 embedding、整篇塞进 prompt。三个理由逐个击毙它：

1. **语义密度**：一篇 3000 字的产品说明混合了定价、售后、FAQ 多个主题，一个向量表达"平均语义"——什么都像，什么都不精。检索要的是"这一段讲退款流程"这样锐利的信号
2. **检索粒度与上下文预算**：top-k 检索命中后要把原文塞给模型，塞整篇文档，k=3 就可能爆窗口；塞 chunk，k=5 还绰绰有余
3. **生成质量**：无关内容稀释注意力——资料堆得越多，模型越容易"引用"到不相干的段落

结论：分块是在**检索精度、上下文预算、语义完整性**之间找平衡的工程动作。

> ☕ Java 视角：这是分页与批处理的老问题——一次喂太多数据既慢又乱，粒度太碎又丢上下文。区别在于数据库分页有明确边界（行），而自然语言的"行边界"（句子/段落/章节）参差不齐，所以分块策略才成了一门手艺。

## 2.2 chunk 大小与 overlap 的权衡

- **太小**（比如几十 token）：语义碎片化。典型事故：上一块结尾是"该政策适用于以下三类人员："，下一块开头是人员列表——检索命中了后半块，模型根本不知道"该"指什么
- **太大**（几千 token）：语义稀释回"整篇文档"的老问题，且 top-k 很快塞满窗口
- **经验起点**：几百 token 量级起步（具体与文档结构、embedding 模型相关），然后**用你自己的评估集调**（L05 会建），不迷信任何魔法数字

**overlap（相邻块重叠）**：相邻块保留 10%-20% 的重叠内容，把"被切断的边界语义"在两块里各存一份——命中任何一块都能看到边界附近的信息。代价是存储与索引略增，几乎总是值得。

## 2.3 三种分块策略

**策略一：固定长度**。按字符/token 数硬切，实现五行。问题：不认识句子边界，"腰斩"事故高发。适合：格式均匀的日志、无结构文本。

**策略二：递归字符分割**（本课主角）。思想：**优先在大的自然边界切，切不下去才降级**：

```
分隔符优先级："\n\n"（段落）→ "\n"（行）→ "。"（句）→ "，" → " "（词）
先用 "\n\n" 切出的段落能装进 chunk 就装；某段超长，降级用 "\n" 切它；
仍超长，用 "。"……直到所有块 ≤ 上限
```

这样切出的块尽量沿自然边界，语义完整度远高于固定切割。LangChain 的 `RecursiveCharacterTextSplitter` 就是这个思想（阶段 3 会遇上它），但我们先手写——十几个函数，写一遍才知道框架帮你做了什么。`code/L02_chunk_demo.py` 有完整实现与两种策略的对比。

**策略三：语义分块**。按内容主题切：相邻句各自 embedding，相似度骤降的地方就是主题切换点，在那儿下刀。效果最好也最贵（每句都要调 embedding），适合主题跨度大、对质量要求高的场景。现在知道思想即可，checkpoint 用策略二足矣。

> 🍿 彩蛋｜行业黑话：管分块叫 chunking，管块叫 chunk——这个词从内存管理（chunk allocation）一路沿用到现在，计算机科学真是万物皆分块。而"递归字符分割"听起来唬人，内核就是"从粗到细找边界"，和你写复杂正则时先按大分隔符 split 再处理子串是同一招。

## 2.4 元数据：chunk 的身份证

每个 chunk 除了正文，还应携带结构化元数据：

```python
chunk = {
    "id": "refund_policy#3",                # 全局唯一 id（引用与增量更新的锚点）
    "text": "退款将在 3-5 个工作日原路返回……",
    "meta": {
        "source": "docs/refund_policy.md",  # 来源文件（引用标注的前提）
        "heading": "售后 > 退款流程",        # 所在标题路径（语境信息）
        "seq": 3,                            # 文内序号（还原上下文顺序）
        "updated": "2026-10-01",            # 更新时间（时间过滤的前提）
    },
}
```

元数据为什么从第一天就要带：**过滤**（"只搜 2026 年的文档"）、**引用**（答案标 [3] 要能指回具体文件具体位置）、**增量更新**（L05：文档变了，靠 chunk 级对比只重嵌入变化部分）——这三个能力全都建立在元数据上，后期补录等于把索引推倒重来。

一个容易被低估的元数据用途：**调试**。检索结果不理想时，带上 heading 与 seq 的元数据让你能立刻看到"命中了哪个章节的哪一段"，进而判断是分块问题还是 query 问题——没有元数据的索引库，调优全靠盲猜。

> ☕ Java 视角：chunk+元数据 ≈ 宽表里的明细行 + 冗余维度列。查询时你要按 source/时间过滤、按 id 关联回原文——没有这些列，检索系统就成了只能全表扫描的裸库。

## 2.5 跑通 code/L02_chunk_demo.py

配套脚本（纯标准库，离线可跑）内置一份带标题与段落的产品说明文档，实现固定长度与递归字符两种分割并排打印：你能直观看到固定切割把"该政策适用于以下三类人员"和人员列表切进两块，而递归分割沿着段落与句子边界下刀。跑完后做讲义练习 1 的实验——改 chunk_size 与 overlap 看块形态变化，"手感"就是这么练出来的。

## 2.6 分块之前的两步：加载与清洗

讲义重点在分块，但实战里**一半的索引质量问题出在分块之前**：

**加载**：按格式选工具——markdown/纯文本直接读；PDF 常用 PyPDF 一类解析库（库名在 HuggingFace/PyPI 可查，API 以官方文档为准）；网页先抽正文再入库。加载的验收标准：每份文档变成"干净的纯文本 + 来源信息"，而不是把二进制噪声带进链路。

**清洗**（按需裁剪，别过度）：

| 动作 | 针对 | 为什么 |
|---|---|---|
| 去页眉页脚/目录/版权行 | PDF、爬取网页 | 重复噪声向量，污染检索 |
| 规范空白与全半角 | 混排文档 | 减少无意义 token |
| 表格转文字描述 | 含表文档 | 表格线性化后语义才完整（"列A: 值1；列B: 值2"） |
| 保留标题结构 | markdown/结构化文档 | 标题是天然的分块边界与元数据（递归分割的第一优先级） |

注意清洗的"度"：去掉的是**与内容无关的重复噪声**，不是自作聪明地删"看起来没用"的段落——你不知道用户将来会问什么。

> ☕ Java 视角：加载与清洗就是 RAG 的 ETL（Extract-Transform-Load）——你在数仓项目里写过的每一课（脏数据治理、格式归一、血缘记录）在这里原样适用。区别只是"数仓治理的是表，RAG 治理的是文本段"。

## 2.7 分块参数速查

| 参数 | 经验起点 | 调整信号 |
|---|---|---|
| chunk_size | 几百 token 量级 | 检索命中但答案碎片化 → 调大；检索不命中率高 → 先查别的再考虑调小 |
| overlap | 块长的 10%-20% | 边界信息常丢失 → 适当加大（存储成本同步涨） |
| 分隔符优先级 | `\n\n` → `\n` → `。` → `，` → 空格 | 按自己文档结构定制（代码文档加缩进层级，对话加说话人标记） |
| 元数据字段 | source/heading/seq/updated | 想用没用上过滤 → 补字段重建索引 |

调参纪律（为 L05 做铺垫）：**一次只动一个参数，评估集跑一遍 hit rate 再动下一个**——否则你永远不知道是哪个改动起了作用。

## 2.8 特殊文档的分块注意

| 文档类型 | 额外注意 |
|---|---|
| 代码文档 | 按函数/类边界切（分隔符加缩进层级），别把函数腰斩 |
| 问答对/FAQ | 一问一答天然是一个 chunk，别再切碎 |
| 表格 | 整表一个 chunk 或行级拆分+表头冗余进每块，二选一，忌讳随机切 |
| 对话记录 | 按说话轮次切，元数据带时间（时间过滤高频需求） |
| 超长单段（合同条款） | 递归分割兜底 + 条款号写进元数据（引用要能指到"第几条"） |

共同规律：**找到文档的"天然语义单元"，让分块服从结构，而不是让结构服从分块**——这也是为什么分块策略没有万能参数，只能对着自己的文档调。

## 2.9 动手实验指引

跑 `code/L02_chunk_demo.py` 的推荐顺序：

1. 先跑默认参数，对照两种策略的输出，找到那个"被腰斩的指代"具体出现在哪一块
2. 把 `CHUNK_SIZE` 改成 60：观察块数暴涨、单块语义变碎——想象检索命中其中一块时模型看到的世界
3. 改成 240：观察"一段多主题"回来了——稀释问题的现场教学
4. 把 `OVERLAP` 改成 0：找到原来靠 overlap 缝合的那条边界信息，看它现在只存在于哪一块

第 4 步做完你会对 overlap 的价值有体感：**它买的是"边界信息的冗余保险"**，这在后面的评估集上会直接体现为 hit rate 的差异。

## 练习

1. 把 demo 的 chunk_size 减半、再加倍，各跑一遍，观察：块数、边界质量、每块语义完整度的变化。
   提示：找一个跨块的指代词（"该政策"/"以上人员"），看两种参数下它离指代对象有多远。
2. 给递归分割器加"标题继承"：切完块后，把所在章节标题路径写进 meta.heading。
   提示：按 "\n#" 先切章节，章节文本再走递归分割，标题一路传下去。
3. 构造一个"固定切割必坏、递归不坏"的极端样例（长段落 + 句中关键指代），用 demo 验证你的构造。
   提示：把指代词与宾语放在固定切割的边界两侧即可构造出来。

## 小结与自测

- 问：为什么不能整篇文档一个向量？答：混合语义导致向量"平均化"，检索信号变钝；且塞满上下文浪费预算。
- 问：chunk 太小与太大的症状？答：太小=指代断裂、语义碎片；太大=语义稀释、窗口吃紧。
- 问：overlap 解决什么问题？答：边界信息在相邻块各存一份，命中任一块都可见边界语义。
- 问：递归字符分割的核心思想？答：按分隔符优先级从粗到细找自然边界，尽量不在语义单元内部下刀。
- 问：元数据为什么第一天就要带？答：过滤、引用、增量更新三大能力都锚在元数据上，后期补录=重建索引。
