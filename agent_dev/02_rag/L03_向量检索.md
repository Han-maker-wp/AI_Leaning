# 第 3 课：向量检索——语义搜索的本质是几何

> 🎬 开场钩子：用户问"怎么退货"，文档里写的是"退款流程"——Ctrl+F 永远找不到这对组合，因为关键词匹配死于同义词。embedding 的魔法是：把两段文本各自变成高维空间里的一个点，这对"同义不同词"的邻居距离很近，而"怎么退货"和"今天天气"被拉到很远。语义搜索没有玄学，全是几何。

⏱ 建议学时：2.5 小时（`code/L03_vector_demo.py` 离线可跑，numpy 即可）

## 本课目标

1. 说清 embedding 的数学本质与"余弦相似度为什么适合文本"
2. 会用 numpy 实现暴力 top-k 检索，并知道它与 ANN（FAISS/Chroma）的分界线
3. 掌握 embedding 模型的选型考量（维度/中英/开源 vs API）
4. 处理好 top-k 与相似度阈值，包括"检索不到就别硬答"的空结果策略

## 3.1 embedding：把语义编码成几何

embedding 模型把一段文本映射为**定长向量**（维度从数百到数千不等，以具体模型卡为准）。关键性质来自它的训练目标：语义相近的文本 → 向量夹角小（余弦相似度接近 1）；语义无关 → 接近正交（接近 0）。中文的"退款流程"、"怎么退货"、"退货退款步骤"在这个空间里抱团，"今天天气不错"被甩到远处。

你数学底子好，直接上度量。两个向量 A、B 的余弦相似度：

```
cos(A, B) = (A · B) / (|A| × |B|)
```

只看方向、不看模长。文本 embedding 通常先做 L2 归一化（|A|=1），此时**余弦相似度退化为点积**，全库检索就是一次矩阵乘法——这就是 numpy 暴力扫快得惊人的原因。为什么用余弦不用欧氏距离：文本向量里"长度方向"常承载词频/篇幅等与语义无关的干扰，只比方向把这些干扰归一掉了（工程上两者普遍正相关，归一化后余弦与欧氏单调等价，不必纠结）。

> ☕ Java 视角：把 embedding 库想成一个**只有一种查询的专用搜索引擎**：insert 时写入向量+原文，query 时给一个向量问"最近的 k 个"。它的索引不是 B+ 树而是 ANN 结构，它的"相关性打分"不是 TF-IDF 而是点积。接口形态完全是你熟悉的 DAO/Repository。

## 3.2 模型选型：三条考量线

- **能力与语言**：中文语料的检索必须验证模型的中英混合能力——用你自己的文档抽 10 对"同义改写"测召回，比看榜单实在
- **开源本地 vs API**：开源模型（如社区广泛使用的 bge 系列，HuggingFace 上可下载）本地跑、免费、数据不出域；API embedding 省事、按量计费。学习与个人项目优先开源本地
- **维度与规模**：维度越高表达越强、存储与计算越贵；几十万 chunk 以下，几百到一千维的模型配合暴力检索完全够用

选型纪律与阶段 0 一脉相承：**先用主流小模型跑通全链路，评估集建立后再换模型对比**——脱离评估谈选型都是玄学（L05 收口）。

> 🍿 彩蛋｜embedding 不是大模型时代的新发明：把词表示成向量、发现"king − man + woman ≈ queen"这类语义可以做算术的现象，在 word2vec 年代就震过学界。现代 embedding 模型（基于 Transformer 架构，原理见主线阶段 3 精读的 arXiv 1706.03762）只是把这件事做到了段落级、多语言级——概念是十年老酒，装进了新瓶子。

## 3.3 检索实现：从暴力扫到 ANN

**第一站：numpy 暴力扫**（你的第一个向量库，几十行）：

```python
import numpy as np

def search(query_vec: np.ndarray, doc_vecs: np.ndarray, k: int = 3):
    """query_vec: (d,)；doc_vecs: (n, d)，已 L2 归一化。返回 top-k 的索引与余弦相似度。"""
    sims = doc_vecs @ query_vec / np.linalg.norm(query_vec)   # 归一化后即点积
    top = np.argsort(-sims)[:k]                               # 取相似度最大的 k 个
    return top, sims[top]
```

复杂度 O(n·d)，10 万级 chunk 在现代 CPU 上毫秒级——**小库用暴力扫就是正确的架构决策**，别过度工程。

**第二站：FAISS**（GitHub 项目 faiss）。专业向量检索库，价值在于 ANN（近似最近邻）索引结构：不追求"精确的前 k 个"，换取亿级向量的毫秒检索。入门路径从精确索引开始（如 `IndexFlatIP` 做内积检索——API 细节以官方文档为准），行为与暴力扫一致，后面按规模需要再换近似索引。**FAISS 是库，不是服务**：管索引、管检索，不管持久化策略、元数据过滤、并发——那些是下面这位的事。

**第三站：Chroma**（GitHub 项目 chromadb）。开箱即用的向量数据库：持久化、文档与元数据随向量同存、检索自带元数据过滤，Python 原生接口，个人项目与原型首选（同样以官方文档为准）。

> ☕ Java 视角：FAISS 之于 Chroma，恰如 **Lucene 之于 Elasticsearch**——一个嵌入库（核心数据结构与算法）与一个开箱服务（持久化/元数据/运维面）的分层。你不会拿 Lucene 裸写生产搜索服务，同样的直觉在这里适用。

## 3.4 top-k、阈值与空结果

检索参数的两道闸门：

- **k 的直觉**：3-10 起步。k 太小漏召回，太大稀释上下文（L01 的教训）
- **max_distance（最低相似度）**：top-k 只保证"库里最相关的 k 个"，不保证"真的相关"。设一条相似度阈值（如"低于 0.3 视为不相关"，具体值依模型分布调），把无关结果挡在 prompt 之外

以及一条常被忽略的工程规则：**检索空结果时的策略要在代码里显式处理**——没有相关资料时，宁可回答"知识库中未找到相关内容"，也不要把不相关的 chunk 硬塞给模型。后者是"模型一本正经胡说"的标准制造流程，也是 L05 忠实度评估要抓的头号目标。空结果不是异常，是检索系统诚实的一半。

## 3.6 MiniVectorStore：你的第一个向量库

把本课机制收进一个 30 行的类——checkpoint 可直接用它当索引层（换 FAISS/Chroma 时接口保持这个形状，上层零改动）：

```python
"""迷你向量库：add + search，自带元数据与阈值过滤。依赖 numpy。"""
import numpy as np


class MiniVectorStore:
    def __init__(self) -> None:
        self._texts: list[str] = []          # chunk 原文
        self._metas: list[dict] = []          # chunk 元数据（L02 的身份证）
        self._vecs = np.zeros((0, 1))         # 占位，add 时重建

    def add(self, texts: list[str], metas: list[dict],
            embeddings: np.ndarray) -> None:
        """批量入库：embeddings 形状 (n, d)，内部做 L2 归一化。"""
        embeddings = embeddings / np.linalg.norm(embeddings, axis=1, keepdims=True)
        self._texts += texts
        self._metas += metas
        self._vecs = np.vstack([self._vecs, embeddings]) if len(self._texts) > len(texts) \
            else embeddings

    def search(self, query_vec: np.ndarray, k: int = 3,
               min_sim: float = 0.0) -> list[dict]:
        """top-k + 阈值过滤；返回空列表是合法结果（L03 的空结果纪律）。"""
        q = query_vec / np.linalg.norm(query_vec)
        sims = self._vecs @ q
        order = np.argsort(-sims)
        return [{"text": self._texts[i], "meta": self._metas[i], "sim": float(sims[i])}
                for i in order[:k] if sims[i] >= min_sim]


if __name__ == "__main__":
    rng = np.random.default_rng(0)
    store = MiniVectorStore()
    store.add(["chunk 甲", "chunk 乙"], [{"id": 1}, {"id": 2}],
              rng.normal(size=(2, 16)))
    hits = store.search(rng.normal(size=16), k=1, min_sim=-1.0)  # 演示用负阈值
    print(hits[0]["text"], hits[0]["sim"])
```

## 3.7 常见坑速查

| 坑 | 症状 | 一句话修法 |
|---|---|---|
| query 与文档用了不同 embedding 模型 | 检索结果全不相关 | 两端必须同模型（向量空间不同构） |
| 忘了 L2 归一化 | 长文档霸榜 | 入库与查询都归一化 |
| 换库没重建索引 | 旧向量查不出 | 模型一换，全量重嵌入 |
| 相似度阈值抄别人家的 | 过滤过严/过松 | 阈值随模型分布定，用自己数据看分布再定 |
| top-k 直接拼 prompt 不去重 | 同一段重复出现 | 相邻重叠 chunk 可能都命中，按 source+seq 去重 |
| 检索结果不含原文只存向量 | 无法组装 prompt | 向量库必须"向量 + 原文 + 元数据"同存 |

这张表加一行总结：向量检索的一切坑都源于一件事——**向量空间是模型给的，你必须遵守它的合同**（同模型、同归一化、同语言分布），合同之外没有奇迹。

## 小结与自测

- 问：embedding 的关键性质？答：语义相近 → 向量方向相近；文本检索用余弦（归一化后即点积）。
- 问：暴力扫与 ANN 的分界线？答：十万级以内暴力扫毫秒级且精确，是正确选择；更大规模才需要 FAISS 类近似索引。
- 问：FAISS 与 Chroma 的定位差异？答：FAISS 是嵌入库（索引算法核心），Chroma 是向量数据库（持久化+元数据+开箱服务）——Lucene 与 Elasticsearch 的关系。
- 问：top-k 之外为什么还要阈值？答：top-k 只保证"最相关的 k 个"，不保证"相关"；阈值挡住无关结果，避免污染生成。
- 问：检索为空时怎么办？答：显式返回"未找到相关内容"，绝不硬塞不相关资料给模型。
