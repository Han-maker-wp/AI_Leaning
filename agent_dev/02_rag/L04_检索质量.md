# 第 4 课：检索质量——RAG 的天花板

> 🎬 开场钩子：用户问"错误码 E4502 怎么处理"，向量检索返回了一堆"错误处理最佳实践"的段落——语义相近，全无用处；而一个朴素的关键词搜索一击命中含 "E4502" 的那一行。精确标识符（错误码/型号/人名/版本号）是语义向量的天生盲区。这不是 bug，是 embedding 的分布性质：罕见 token 的组合在向量空间里没有足够"辨识度"。解法就是今天的主题：别把宝押在单一通道上。

⏱ 建议学时：2 小时

## 本课目标

1. 会把检索失败归类为 recall 问题（查不到）与 precision 问题（查不对），并按类下药
2. 理解混合检索的互补逻辑，会手算 RRF 融合
3. 说清 bi-encoder 与 cross-encoder 的差异，会设计两阶段检索（召回→精排）
4. 会用查询改写（含指代消解与 HyDE 思路）救活口语化与多轮提问

## 4.1 先诊断，再下药

检索失败只有两类，药方完全不同：

| 失败类型 | 症状 | 病因 | 药方 |
|---|---|---|---|
| **查不到**（recall 不足） | 正确的 chunk 根本没进 top-k | 分块切坏了 / query 与文档措辞差距大 / 单通道盲区 | 混合检索、查询改写、调分块 |
| **查不对**（precision 不足） | 正确的 chunk 进了 top-k 但排在后面，或混入大量无关块 | 语义相近但实际无关（E4502 案例） | rerank 精排、阈值过滤 |

诊断工具就是 L05 的评估集（hit rate 看 recall，MRR 看 precision）。本课的四个手段，每一个都对应上表的一格——先定位，再用药，不盲目堆技术。

> ☕ Java 视角：这套"召回/精排"话语体系直接继承自搜索与推荐系统：召回（千级）→ 粗排（百级）→ 精排（十级）→ 重排，一条漏斗。LLM 检索把漏斗简化成两三级，但思想没变——**便宜的粗筛放开 recall，昂贵的精算保住 precision**，和你写"SQL 粗筛 → 内存精算"是同一个分层直觉。

## 4.2 混合检索：关键词 + 向量互补

两路各自的不可替代性：

- **关键词路（BM25）**：精确匹配的王者。"E4502"、"v2.3.1"、"张伟"这类精确标识符，词面命中就是最强信号。BM25 是经典打分函数：TF-IDF 思想（词越稀有越重要、出现越多越相关）加上文档长度归一（防长文档靠篇幅堆分）。不必会推导，记住定位：**词面匹配，抗语义盲区**
- **向量路**：语义匹配的王者。"怎么退货" vs "退款流程"只有它能连上

两路各自出一份 top-k，然后要**融合成一个排序**。工业界最常用的是 RRF（Reciprocal Rank Fusion，倒数排名融合）——它只看每路的排名，不看分数（两路分数量纲完全不同，直接相加毫无意义）：

```
某 chunk 的 RRF 得分 = Σ各路 1 / (k + 该路排名)     （k 常取 60，缓解头部排名的权重碾压）
```

手算一遍就懂：chunk X 在向量路排第 1、关键词路排第 3；chunk Y 只在向量路排第 2、关键词路未上榜——

```
X: 1/(60+1) + 1/(60+3) ≈ 0.01639 + 0.01587 = 0.03226
Y: 1/(60+2)            ≈ 0.01613
```

X 胜出：**两路都说好 > 单路第一**。这正是我们想要的偏好，而且 RRF 免调权重（对比加权融合要拍两个 λ），工程起点首选。

## 4.3 rerank：两阶段的贵精算

向量检索（embedding 召回）的模型结构是 **bi-encoder**：query 和文档**各自独立**编码成向量再比距离——快（文档向量可离线算好、可入库），但因为两边从没"见过面"，匹配精度有天花板。

**cross-encoder** 反过来：把 query 和文档**拼在一起**送进模型，直接输出一个相关性分——模型逐 token 交互地"对照着读"，精度显著更高；代价是每对 (query, doc) 都要跑一次前向，**无法预计算**，百万文档全库 cross-encode 等到天荒地老。

于是两阶段成了标准架构：

```
全库（10 万 chunk） --bi-encoder 向量召回--> top-50 --cross-encoder rerank--> top-5 进 prompt
```

粗召回放开 recall（多捞一些别漏），精排守住 precision（把真正相关的顶上去），贵的技术只用在最后一小撮上。工程上 rerank 模型有现成开源选择（如社区常用的 bge reranker 类模型，HuggingFace 可下），接入形态就是一个打分函数。

> ☕ Java 视角：**数据库的"索引粗筛 → 回表精算"** 同构复现：secondary index 把范围缩小到几十行，再回表取完整行做精确判断。cross-encoder 就是那个"回表后的逐行判断"，慢而准，所以永远放在漏斗末端。

## 4.4 查询改写：救活问题本身

很多检索失败该改的是 query，不是库。三种常用手术：

1. **口语化改写**："咋弄啊这个" → "如何操作退款流程"。用户的输入分布与文档的书面语分布天然错位，先让 LLM 把 query 翻译成"文档腔"
2. **多轮指代消解**：用户上一轮问"PyTorch 怎么安装"，这一轮问"它支持 Windows 吗"——拿原 query 去检索，"它"直接把向量带偏。先让 LLM 结合历史把问题补全成完整独立问题，再检索。**Agent 场景标配**，因为用户天然用对话方式用你的 RAG
3. **HyDE 思路**（Hypothetical Document Embeddings）：反直觉但有效——先让模型针对 query **编一个假设性答案**（哪怕细节是错的），再拿这个"答案"去向量库里找相似文档。原理：答案与文档在同一个"文本分布"里（都是书面陈述句），比问题与文档的分布距离近得多。查询改写的奇招，评估集上值得 A/B 一次

> 🍿 彩蛋｜行业黑话里 rerank 常被叫"精排"，HyDE 则有个形象的诨名："让模型先打草稿再抄书"。检索工程圈的许多名词都继承自搜索时代——毕竟在 LLM 之前，这群工程师已经在与"query 太短、文档太长、相关性玄学"搏斗了二十年。

## 4.5 别忘了元数据过滤

混合与精排之外，还有一个便宜而高效的收口：**先用元数据把检索池缩小**（L02 埋的伏笔）。时间（"只搜今年更新的文档"）、来源（"只在合同目录里找"）、权限（"只搜该用户有权看的文档"——这同时是安全问题，过滤必须在检索层强制执行，阶段 4 L03 详论）。过滤后再做向量检索，又快又准，且天然规避"越权检索出敏感 chunk"的事故。

三个高频过滤例子，感受一下它的性价比：

- 时间过滤：`updated >= 2026-01-01`——政策类知识库"只要最新版"是刚需
- 来源过滤：`source LIKE 'contracts/%'`——"合同问题只在合同目录里找"
- 权限过滤：`doc_id IN (用户可见文档集)`——检索层强制执行，不依赖模型自觉

## 4.6 组合拳：一次问答的完整数据流

把本课四个手段串成一条链（哪些上、哪些不上，按评估指标决定）：

```
用户问题（多轮）
   │
   ▼
[查询改写] 指代消解 + 口语化改写 ──（进阶：HyDE 生成假设答案）
   │
   ▼
[元数据过滤] 时间/来源/权限缩小检索池
   │
   ├──▶ 向量路（bi-encoder）── top-20 ─┐
   │                                    ├─▶ [RRF 融合] ─ top-50
   └──▶ 关键词路（BM25）──── top-20 ──┘        │
                                               ▼
                                    [cross-encoder rerank] ─ top-5
                                               │
                                               ▼
                                    组装 prompt（带编号资料）→ 生成
```

两路对比的本质，一张表说尽（这张表同时是"要不要上混合检索"的决策依据）：

| | 关键词路（BM25） | 向量路（bi-encoder） |
|---|---|---|
| 强项 | 精确标识符、罕见词、代码名 | 同义改写、跨语言、口语提问 |
| 弱项 | 同义词盲区（退货≠退款） | 罕见 token 辨识度低（E4502） |
| 成本 | 纯本地、无需模型调用 | 需要 embedding 计算 |
| 什么时候单路就够 | 文档全是编号/型号类内容 | 纯闲聊式知识问答 |

**何时上 rerank 的判断**：先把混合检索做好并跑评估——如果 hit rate 高但 MRR 低（正确资料总在 top-k 里但沉底），rerank 是对症药；如果 hit rate 本身低（根本没捞到），钱该花在召回侧（改写/分块），rerank 无米下锅。

> ☕ Java 视角：整条链就是经典的**管道-过滤器架构**：每个环节单一职责、可独立测试、可按需插拔。评估集就是每个 filter 的单元测试；"何时上 rerank"就是"何时给管道加一层缓存"——先 profiler（评估指标）后优化，全世界的性能优化纪律都是同一条。

## 4.7 查询改写三例（改写前 → 改写后）

| 场景 | 原始 query | 改写后 | 生效机制 |
|---|---|---|---|
| 口语化 | "咋弄啊这个退款" | "退款流程如何操作" | 对齐文档书面语分布 |
| 多轮指代 | （上轮问安装）"它支持 Windows 吗" | "PyTorch 支持 Windows 安装吗" | 指代消解补全 |
| 需求模糊 | "太贵了有没有别的办法" | "该产品的免费额度与降配方案" | 意图显式化 |

三个实现要点：① 改写本身是一次独立的 LLM 调用（输出是新的 query，结构化输出保护它别夹解释）；② 改写要有"熔断"——改写失败就用原 query 检索，别让辅助功能变成单点故障；③ 改写结果进日志——检索突然变差时，第一个怀疑对象就是改写层（它悄悄改变了输入分布）。

> ☕ Java 视角：改写层就是管道里的**适配器 filter**：把"用户方言"翻译成"检索引擎方言"。独立、可测、可旁路（熔断直通），三个形容词决定了它是个好组件而不是一个坑。

给"什么时候需要查询改写"一个判断信号收尾：翻评估集里**查不到（hit rate 低）的案例**——如果原始 query 本身口语化、带指代、或与文档用词体系差异大，改写是对症药；如果 query 已经清晰但仍查不到，病根在分块或文档覆盖，改写帮不上。**工具服务于诊断，诊断先于工具**——本课四个手段没有一个是"必上"的，都是"指标指向哪才上哪"。

## 练习

1. 手算 RRF：chunk A 向量路第 2、关键词路第 7；chunk B 向量路第 1、关键词路未上榜（k=60）。谁赢？
   提示：未上榜那项贡献为 0；比较 1/62+1/67 与 1/61。
2. 给 mini 检索脚本加一个简单混合：字符 bigram 相似度当"语义路"、精确子串匹配当"关键词路"，RRF 融合。
   提示：两路各出 top-10 的 (chunk_id, rank) 列表，套公式合并排序。
3. 写指代消解的改写 prompt：输入最近三轮对话 + 当前问题，输出完整独立问题。造 3 个多轮案例验证。
   提示：明确要求"把代词替换为具体对象，输出单个问句，不要解释"。

## 小结与自测

- 问：向量检索的盲区？答：精确标识符（错误码/型号/人名）——罕见 token 组合在向量空间辨识度不足，需要关键词路补位。
- 问：RRF 为什么不用调权重？答：只用排名倒数求和，回避了两路分数量纲不可比的问题，免拍 λ。
- 问：cross-encoder 为什么慢？答：每个 (query, doc) 对都要现场跑一次前向，无法预计算；所以只能用在漏斗末端。
- 问：bi-encoder 与 cross-encoder 的取舍？答：bi-encoder 快而粗（可离线建库），cross-encoder 慢而精——两阶段漏斗各取所长。
- 问：HyDE 的原理？答：假设答案与文档同分布（书面陈述句），拿"答案"找文档比拿"问题"找文档距离更近。
