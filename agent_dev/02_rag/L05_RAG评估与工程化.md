# 第 5 课：RAG 评估与工程化——没有度量就没有优化

> 🎬 开场钩子：「感觉检索变准了」不叫评估，叫玄学。你把 chunk 从 300 调到 500、换了 embedding 模型、加了 rerank——三个变量一起动，效果是好是坏？没有评估集，你只能"上线试试"。这等于不写单测就重构：改了，但不知道改好还是改坏。今天给 RAG 补上单测，顺便把它从 demo 推进到能长期运行的系统。

⏱ 建议学时：2.5 小时（本课的评估集就是你 checkpoint 的验收仪表盘）

## 本课目标

1. 会构建检索评估集（≥20 条问答对），会算 hit rate 与 MRR
2. 会用规则化 rubric 写 LLM-as-judge 评估忠实度，并知道它的三大坑
3. 会实现引用标注（含后校验），说清它对信任与调试的价值
4. 会做 chunk 级增量更新，处理最容易被漏掉的"删除"

## 5.1 评估集：RAG 的模拟考卷

评估集 = 一组 (问题, 标准答案, 出处 chunk id)：

```
Q1: 退款多久到账？  A1: 3-5 个工作日原路返回  出处: refund_policy.md#3
Q2: 企业版支持几个成员？ A2: ...             出处: pricing.md#2
```

构建三策：① 从文档人工出题（保底动作，20 条起步，覆盖不同文档与难度）；② 收集真实用户问题（最值钱——分布对齐，坏例尤其值钱）；③ 让 LLM 批量生成再人工筛（快，但注意别全是"文档腔"的简单题）。

有了卷子，**先考检索再考生成**（L01 的原则落地）：

- **hit rate@k**：正确出处 chunk 是否出现在 top-k 里。命中率 = 覆盖率问题（recall）的温度计
- **MRR**（Mean Reciprocal Rank）：正确 chunk 排名 r，得分 1/r，全平均。正确结果排第 1 得 1 分、第 2 得 0.5、第 5 得 0.2——它同时惩罚"进了 top-k 但沉底"的 precision 问题

这两个指标**不需要 LLM 判分**：便宜、秒级、可复跑、每次改配置都能刷一遍——它们是你调参的主仪表盘。

> ☕ Java 视角：评估集就是你的**回归测试套件**，hit rate/MRR 是断言通过率。从此改分块参数、换模型、加 rerank 都是"跑一次测试"而不是"上线试试"。阶段 4 L02 会把它升级成带 CI 心智的 Evals 体系。

## 5.2 生成侧评估：忠实度与 LLM-as-judge

检索对了，还要问生成对不对。三个维度：

- **忠实度（faithfulness）**：答案是否**只**基于检索到的资料——治幻觉的核心指标。答得流畅但夹带资料外的"编造"，就是不忠实
- **答案相关性**：答的是不是问的问题（答非所问与幻觉要分开统计，药方不同）
- **引用正确性**：标注 [2] 的句子，资料 2 是否真的支撑它

评估方式主流是 **LLM-as-judge**：用（通常更强的）模型按给定 rubric 打分。工程要领在 rubric 的写法：

```
差的 rubric：请给答案的准确性打 1-10 分          ← 分数漂移，重跑一次换一个数
好的 rubric：请逐句判断：该句能否被给定资料支持？
             输出 JSON: {"supported": 句数, "unsupported": 句数, "unsupported_detail": [...]}
             ← 判断题代替打分题，输出可校验、可复跑
```

三大坑与对策：**分数漂移**（同输入两次打分不同）→ 用判断题/排序题代替开放式打分；**位置偏差**（偏爱排在前面/更长的答案）→ 对比评估时交换顺序跑两遍取平均；**自我偏好**（偏爱自己风格的输出）→ 评估模型与被评模型异源。最后一条纪律：**judge 的结论是统计信号，不是真理**——抽样做人工复核，校准 judge 的可信度。

> 🍿 彩蛋｜LLM-as-judge 像极了"自动化 code review"：能抓大头（明显的越权、幻觉、漏引用），但会把"风格之争"也当问题报出来，偶尔还前后不一致。所以工程界的用法惊人一致：judge 管量（全量跑），人管质（抽样校准 + 处理上诉）。

## 5.3 引用标注：信任与调试的基础

让答案的每句结论带 `[n]` 溯源到第 n 条检索资料：

1. **生成侧**：prompt 明确要求"每个事实性结论后标注 [资料编号]，资料不足以支撑时明说"（L03 格式约定的老手艺）
2. **后校验**（关键）：代码检查每个 [n] 是否落在实际检索结果范围内——模型会引用不存在的 "[7]"；再抽查被引资料是否支撑对应句子（可复用 5.2 的 judge）
3. **呈现侧**：[n] 可展开/跳转到具体 chunk 与源文件位置（L02 元数据在这里收口）

引用的价值是双重的：**用户敢信**（可验证），**你能调试**——答案错时一眼定位是检索错了（引了错的资料）还是生成错了（资料对但答歪了），这两类的修法完全不同。

## 5.4 增量更新：文档会变

知识库不是建完就完的工程。文档变更的三种情况与对策：

- **修改**：按 chunk 内容哈希对比（L02 的 chunk id 在此发力）——内容没变的 chunk 跳过，变了的重新 embedding 覆盖入库
- **新增**：新文档走一遍分块+embedding+入库
- **删除**（最容易漏）：文档删了，它对应的 chunk 必须从库里清掉，否则变成"僵尸知识"——检索命中一个已删除的段落，答案引用一个不存在的文件，用户对系统的信任当场清零。对策：以"来源文件 → chunk 清单"的映射为准，重建/同步时先删后加

触发方式从手动脚本起步（够用），量大了再上事件驱动（文档系统 webhook → 触发增量索引）。配上一节 L04 的元数据过滤（时间戳），你还能做"只检索最新版本"这类策略。

线上运行的最后一块：**监控最小集**——每次问答记录延迟、token 成本、检索空结果率、引用率（答案平均引用几条）。这四个数字的健康度，就是知识库系统的健康度（阶段 4 L01 的可观测体系会把这些接进 tracing）。

## 5.7 指标速查与评估集自检

| 指标 | 测什么 | 合格线怎么定 |
|---|---|---|
| hit rate@k | 正确资料是否进 top-k（recall） | 看业务容错：答案引用错资料代价高就要高线 |
| MRR | 正确资料排名质量（precision） | 与 hit rate 的差距 = rerank 的潜在收益 |
| 忠实度 | 答案是否忠于资料（幻觉率） | 不支持句数为 0 是硬要求方向 |
| 引用正确性 | 被引资料是否真支撑句子 | 抽检合格率，错配必须修 |
| 空检索率 | 多少问题检索为空 | 突增 = 文档或分块出了问题 |

评估集质量自检四问（卷子本身不合格，分数全是假象）：① 题目覆盖了所有重点文档吗（别全押在一篇上）？② 难度分层了吗（有简单直答题，也要有需要跨文档拼装的题）？③ 有"库里没有答案"的陷阱题吗（考空结果处理与忠实度）？④ 标准出处标注对了吗（出处错，hit rate 全废）？

增量更新的核心代码骨架（先删后加，简单且不漏）：

```python
"""增量更新骨架：以文件为粒度先删后加。chunk 哈希避免无谓重嵌入。"""
import hashlib


def file_fingerprint(chunks: list[str]) -> str:
    """整文件的 chunk 内容指纹：变了才需要动这个文件的索引。"""
    joined = "\n".join(chunks)
    return hashlib.sha256(joined.encode("utf-8")).hexdigest()


def sync_file(store, source: str, chunks: list[str], old_fp: str | None) -> str:
    """文档变更同步：先删该来源全部旧 chunk，再入库新 chunk（先删后加，防僵尸）。"""
    new_fp = file_fingerprint(chunks)
    if old_fp == new_fp:
        return old_fp                                   # 未变化：零成本跳过
    store.delete_by_source(source)                      # 关键一步：删除旧 chunk
    store.add(chunks, metas=[{"source": source, "seq": i} for i in range(len(chunks))])
    return new_fp
```

> ☕ Java 视角：评估集 = 回归测试套件，指标 = 断言，judge = 自动化 code review，增量更新 = 缓存失效策略（hash 比对 + 先删后加的原子替换）。RAG 工程化的每个环节都能在你写过的 Java 系统里找到原型——这门手艺你早就会了一半。

## 5.8 上线前检查清单

知识库问答系统交差前的最后一遍（checkpoint 验收同用）：

- [ ] 评估集 ≥20 条，含陷阱题（库里无答案类）；hit rate@5 / MRR 有基线数字
- [ ] 忠实度 judge 跑过全量，不支持句有处理路径（收紧 prompt / 补资料）
- [ ] 每个答案的引用可点回源文件；引用了不存在编号的 bug 已修（后校验生效）
- [ ] 空检索有明确话术，不硬答
- [ ] 索引持久化：二次启动不重建全量索引
- [ ] 文档"修改/新增/删除"三种变更都验证过（删除最容易翻车——僵尸知识）
- [ ] 延迟 / 成本 / 空检索率 / 引用率四个监控数字可查
- [ ] 换一份新文档，不改代码能完成入库并答对相关问题（泛化性，不是背库）

最后一项最容易被跳过也最能暴露问题：系统应该是对"任何文档"的知识库，而不是对"这份文档"的背诵器。

2. 写规则化忠实度 judge：输入（资料列表 + 答案），输出逐句支持/不支持的 JSON。用 L04 的容错解析处理它的输出。
   提示：这就是阶段 0 结构化输出的综合复用——你会发现那套三层防御在哪都要用。
3. 实现增量更新：给索引库加"内容哈希 → chunk id"表，文档变更时只处理差异，并显式处理删除。
   提示：以文件为粒度做"先删后加"最简单也最不容易漏，先跑通再优化到 chunk 粒度。

## 小结与自测

- 问：为什么先测检索再测生成？答：检索是上游且指标便宜可复跑；检索不命中，生成评估没有意义。
- 问：MRR 怎么算、惩罚什么？答：正确 chunk 排名 r 得 1/r 再平均；惩罚"进了 top-k 却沉底"的精排问题。
- 问：LLM-as-judge 三大坑与对策？答：分数漂移（改判断题）、位置偏差（换序跑两遍）、自我偏好（评估与被评异源）。
- 问：引用标注为什么要后校验？答：模型会引出不存在的编号或张冠李戴，代码层校验是承诺兑现的保证。
- 问：增量更新最易漏的是什么？答：删除——不清掉对应 chunk 就会产生"僵尸知识"，比没有知识库更伤信任。
