# 第 1 课：框架地图——五个名字，一句话说清

> 🎬 开场钩子：2023 年 3 月，AutoGPT 开源后一度成为 GitHub 历史上增长最快的项目之一，star 曲线几乎垂直——所有人相信"自主 Agent 框架"就是下一个 Spring。不到一年，热潮明显退去：大部分用 AutoGPT 起步的团队，最后要么弃坑，要么换成自己写循环。框架没有错，错的是"按热度选型"。这节课我们把市面上主要的 Agent 框架放进一张地图，你以后选型，按问题形状选，不按 star 数选。

⏱ 建议学时：1.5 小时

## 本课目标

- 说出 LangChain / LangGraph / LlamaIndex / AutoGen / CrewAI 各自的一句话定位与典型适用场景
- 解释"框架层"到底封装了什么——裸写循环的哪些痛点是真实的，哪些是被夸大的
- 给出三类场景（学习期 / 原型期 / 生产期）各自的选型倾向
- 列举至少三个"裸写更好"的信号
- 掌握"十分钟评估一个新框架"的检查清单，并知道去哪里找弃坑者的复盘

## 一、为什么会有框架层：裸写到底痛在哪

阶段 1 你手写过 function calling 循环。回头看，那个循环只解决了最核心的 30%：发请求、解析 tool call、执行、拼回消息。真实项目里还有 70% 的"外围工程"：

1. **重试与超时**：LLM API 会限流、会 500，裸 `requests` 一崩全崩
2. **状态管理**：对话历史越来越长，什么时候截断、怎么摘要，散落在循环里很难维护
3. **流式输出**：用户要"打字机效果"，你就得处理 SSE 分片、工具调用与文本的交错
4. **可观测**：一次回答背后有 5 次模型调用、3 次工具调用，出了问题从哪查
5. **结构化输出**：你想要 JSON，模型偏偏偶尔给你"好的，以下是 JSON："
6. **换模型**：今天用 A 家，明天想对比 B 家，调用协议不一样
7. **评估闭环**：改了一版 prompt，到底变好没好——肉眼比对几十条输出撑不过三天

框架层的价值主张就是：这些外围工程我包了。听起来很熟？

> ☕ Java 视角：这就是 Spring 之于 Servlet 的故事。你完全可以用裸 Servlet 写 Web 应用（就像你用裸 API 写 Agent），但连接池、事务、异常映射这些"每个项目都要写一遍"的东西，最终总会长成一个框架。Agent 框架现在处于"早期 Spring"阶段——抽象还在剧烈变化，这是它和成熟 Spring 最大的区别。

## 二、五大框架一句话定位

| 框架 | 一句话定位 | 典型场景 | 不适合 |
|---|---|---|---|
| LangChain | LLM 应用"全家桶"：模型/提示/输出/记忆/RAG 的统一抽象层 | 快速拼装原型，想要现成集成最多 | 逻辑复杂后，胶水层会成为调试负担 |
| LangGraph | 图编排引擎：把 Agent 写成显式状态机（节点+边+共享状态） | 多步循环、带分支审批流的 Agent | 线性无循环的一次性任务 |
| LlamaIndex | 以"数据接入+索引"为中心的 RAG 框架 | 文档问答、知识检索为主的应用 | 以工具调用为主的流程型 Agent |
| AutoGen | 微系出的多 Agent 对话框架：Agent 之间互相发消息推进任务 | 研究/原型多 Agent 会话 | 需要严格流程控制的生产系统 |
| CrewAI | "船员"隐喻：定义角色（角色/目标/背景），crew 分工执行 | 角色分工明确的多 Agent 自动化 | 需要精细状态控制的场景 |

两个必须说清的关系：

- **LangChain 和 LangGraph 同门但不同层**。LangChain 管"单步怎么调"（模型抽象、提示模板、解析器），LangGraph 管"多步怎么连"（图、状态、循环）。生产里常见的组合是：核心循环用 LangGraph，单步调用用 LangChain 的模型抽象——或者干脆单步也裸写。
- **LlamaIndex 和 LangChain 的竞争区在 RAG**。阶段 2 你已经手写过 RAG，回头看这两个框架会非常清醒：LlamaIndex 把"文档 → 切块 → 向量 → 检索"这条链封装得很顺；LangChain 也能做，但它是众多能力之一。
- **AutoGen 和 CrewAI 都做多 Agent，哲学不同**。AutoGen 靠"对话"推进——agent 之间互相发消息直到任务完成，灵活但轨迹难控；CrewAI 靠"角色分工"——先定义好角色与工序，更像排班表。L05 讲的四种模式里，前者天然贴近辩论、后者贴近流水线。

### 十分钟评估一个新框架的清单

Agent 框架层出不穷，你不可能每个都系统学。遇到新名字时，花十分钟按这个顺序看（顺序很重要）：

1. **首页的一句话定位**：它声称解决什么问题？对照你手头的真实需求，是真需求吗
2. **快速上手的第一个示例**：它的"最小回路"是什么形状——是链（LangChain 系）、图（LangGraph 系）还是对话（AutoGen 系）？这个形状决定你的心智模型
3. **它的"hello world"有多少行**：超过 30 行才能跑通最简单用例的框架，学习税通常很重
4. **更新频率与破坏性变更记录**：changelog 里搜 breaking / removed / renamed，出现密度告诉你升级痛苦指数
5. **搜一下"remove X from production"**：别人弃坑的复盘帖是最便宜的一手情报

十分钟不一定能决定"用"，但足够决定"要不要再花一小时"。

> 🍿 彩蛋｜LangChain 的诞生：LangChain 由 Harrison Chase 于 2022 年 10 月开源——那时 ChatGPT 还没发布。它最初解决的是"把 LLM 链起来"这个朴素问题（名字里的 chain 就这么来的），后来长成了庞大的全家桶。你在 GitHub 搜 langchain 能看到它今天的规模。

## 三、选型：按问题形状选，不按热度选

把你的需求先压缩成三个问题：

1. **你的流程是线性的还是带循环分支的？** 线性（固定 pipeline）裸写或轻量组合就够；有循环、有"人工审批后继续"这种分支，才值得上 LangGraph 这类图引擎。
2. **你的核心难点是数据还是流程？** 难在"把一堆异构文档喂进去检索"，LlamaIndex；难在"多个步骤怎么可靠地串起来"，LangGraph；两者都不难（demo），LangChain 最快。
3. **多 Agent 是真需求还是想象中的酷？** 先问：单 Agent + 多工具能不能解决？绝大多数任务可以（阶段 1 你已验证）。真需要多个角色协作时再进 L05。

三个问题答完，选型常常已经自动出结果了。举个对照：同样是"文档问答"，如果你要的是一个内部知识库问答服务（固定"检索→生成"两步），裸写或 LlamaIndex 都舒服；如果你要做的是"帮我把这份合同审完，可疑条款要查外部法规库，最后生成报告给人确认"——流程有分支、有审批，就该看 LangGraph。

> 🍿 彩蛋｜"多 Agent"这个词的黑话陷阱：行业里把"一个模型调一堆工具"叫 Agent，把"多个模型角色互相配合"叫 multi-agent。但产品宣传里经常混着用拉高估值感。判断标准很简单：**进程里有几个独立的对话上下文**。一个上下文再花哨也是单 Agent。

> ☕ Java 视角：选型逻辑和你当年在 Spring MVC / Dropwizard / Vert.x 之间做选择一模一样：全家桶买的是"开箱即用+生态"，代价是"理解它的抽象成本"；轻量库买的是"可控"，代价是"轮子自己造"。没有银弹，只有 trade-off——这句行业黑话在哪个领域都成立。

## 四、什么时候裸写更好

这三个信号出现任何两个，就认真考虑裸写：

1. **流程短且稳定**：三步以内的固定流程（如"检索→生成→格式化"），裸写一百行，框架反而引入一堆间接层
2. **调试透明度要求高**：出了问题你必须能在一屏代码里看清每次发给模型的完整 prompt。框架的抽象层数越多，"模型到底收到了什么"越难一眼看到
3. **性能与成本敏感**：框架的默认实现（如历史管理、重试策略）不一定贴合你的场景；token 是真金白银，多包一层抽象往往多几处"顺手多塞的上下文"

还有一条隐藏收益：**裸写让你真正理解机制**。阶段 1 的手写循环不是白费的——正因为你手写过，现在看任何框架源码都能对上号。反过来，只会框架的人离开框架就寸步难行。

## 五、给你的学习顺序建议

本阶段的走法（也是这份建议的理由）：

1. **先 LangGraph，后 LangChain 细节**。你的心智模型里"循环+工具"已经有了（阶段 1），LangGraph 是把它显式化，学习曲线最顺；LangChain 的抽象细节（L02）在有了图思维之后更好理解——知道每段胶水"住在流程的哪一步"
2. **每学一个框架特性，都问"裸写时这对应什么"**。对不上的特性要警惕：那可能是为框架自身存在而设计的，不是为你的问题存在的
3. **看框架源码只看两层**：入口层（它怎么组装请求）和默认值层（它替你做了哪些决定）。这两层恰好是 L06 决策框架要用的证据，其余实现细节先跳过

一条时间线上的提醒：不要试图"学完五个框架再动手"。本阶段只深挖 LangGraph 一个（配合 L02 的 LangChain 局部），其余的知道定位与何时回头看即可——框架会过时，"按形状选型"的方法不会。

> ☕ Java 视角：这和你读 Spring 源码的策略相同——先看 `DispatcherServlet` 和 `BeanPostProcessor` 这些扩展点，别一头扎进 AOP 字节码。读源码的目的是获得"它在哪里替我做决定"的地图，不是背实现。

## 六、一张速查决策图

把前四节压缩成一张可以贴在显示器边的图（从上往下问，命中即停）：

```
你的需求是什么形状？
│
├─ 固定线性短流程（≤3 步，无人工介入）
│    └─→ 裸写：阶段 1 的循环 + 阶段 2 的检索，一百行内解决
│
├─ 难点在"异构数据怎么喂进来检索"
│    └─→ LlamaIndex（或：裸写 RAG 也完全够，见阶段 2）
│
├─ 有循环 + 分支 + 人工审批（流程是主角）
│    └─→ LangGraph（本阶段 L03 主课）
│
├─ 多角色分工、互相协作（确认不是伪需求后）
│    └─→ 先读 L05 识别模式，再选工具（AutoGen/CrewAI 或 LangGraph 手搭）
│
└─ 都不确定，只想快点拼个能演示的东西
     └─→ LangChain 全家桶，快就是一切（但记住 L02 的批判清单）
```

使用纪律：**每次选型，把你的答案写在需求文档第一段**——三个月后你会感谢今天写下的理由，无论是被验证还是被打脸，都是认知资产。

最后一条诚实提示：这张图帮助你**排除明显错误的选择**，不保证给出唯一最优解。真到两个选项难分难下的场合，用最便宜的实验裁决——各花半天写个原型跑同一组测试问题，比再读一周文档更接近真相。

## 练习

1. 用一张表（写进笔记）把五大框架按"你的当前项目需要度"排序，每个写一行理由。
   提示：先写下你真实想做的那个 Agent 的流程形状（线性？循环？多角色？），再对着第二节三个问题套。
2. 打开 LangChain 官方文档（python.langchain.com）的 API 目录，只看类名不细读，统计一下从"模型调用到结构化输出"路径上要经过几个抽象类。
   提示：数一数 ChatModel、PromptTemplate、OutputParser 之外还有哪些 xxxRunnable。
3. 找一个你用过的 Agent 产品（如编码助手），反推它更像五种模式里的哪种，说明判断依据。

4. 用第六节的决策图回答三个 hypothetical 需求：a) 周报生成器（读 Jira → 写总结）；b) 合同审核（分支+审批）；c) 个人文档问答。把"答案+命中的分支"写成三行。
   提示：a 想想是否真需要框架——固定两步流程；b 是图引擎的教科书场景；c 阶段 2 你已经裸写过一遍了。

## 小结与自测

- Q1：LangChain 和 LangGraph 的分工边界是什么？
  一句话：LangChain 管"单步怎么调 LLM"（模型/提示/解析抽象），LangGraph 管"多步怎么连"（图、状态、循环、中断）。
- Q2：框架层封装的外围工程里，哪三类你在阶段 1 裸写时亲身体会过痛点？
  一句话：重试/超时、状态管理（历史截断）、结构化输出（任举三类即可）。
- Q3：判断"多 Agent 是不是真需求"的标准是什么？
  一句话：是否真的需要多个独立的对话上下文/角色分工，单 Agent+多工具解决不了的才算。
- Q4：列举两个"裸写更好"的信号。
  一句话：流程短且稳定；调试透明度要求高（性能成本敏感也算）。
- Q5：评估一个新框架的十分钟清单，第一步看什么？
  一句话：先看它的一句话定位与自己的真实需求对不对得上——需求都不匹配，后面的考察全是白费。
