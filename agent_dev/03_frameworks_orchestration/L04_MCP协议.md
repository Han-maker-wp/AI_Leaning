# 第 4 课：MCP 协议——给工具世界定一个"USB 接口"

> 🎬 开场钩子：算一笔账：你有 3 个 Agent 应用（IDE 助手、客服机器人、数据分析 agent），想让它们各接 5 个工具（文件系统、GitHub、数据库、Slack、搜索）。如果每家应用和每个工具都要单独写一遍适配，就是 3 × 5 = 15 份胶水代码；再来一个新应用，再加 5 份。2024 年 11 月，Anthropic 发布并开源了 MCP（Model Context Protocol）试图把这个 N × M 问题变成 N + M：工具方写一次 server，应用方接一次 client，中间靠协议对话。这也是你作为 Java 老兵最该眼熟的故事——标准的胜利从来都是生态的胜利。

⏱ 建议学时：2 小时

## 本课目标

- 用 N×M 适配器问题解释 MCP 存在的必要性
- 画出 MCP 的基本结构：host / client / server，说清 stdio 与 HTTP 两种传输方式的适用场景
- 列出 MCP server 的三类原语（tools / resources / prompts）各自服务什么需求
- 动手：装一个官方或社区现成的 MCP server，用一个 MCP client（如支持 MCP 的桌面应用或 CLI）连上它跑通一次工具调用
- 判断自己的项目"该暴露 MCP server 还是只写内部函数"

## 一、问题：N × M 适配器地狱

阶段 1 你给迷你 Agent 写工具时，工具就是 Python 函数，schema 手写 JSON。这在"一个应用、三五个工具"时完全够用。但工具生态一旦大起来：

- **工具方**（做数据库连接的、做浏览器控制的）要为每种宿主应用单独适配：这家用 JSON schema、那家用 YAML，调用协议各家私有
- **应用方**（做 IDE 助手的、做客服系统的）每接一个新工具都要读一次它的私有文档
- **用户**（你）在每个应用里重复配置同一批工具的密钥

和你在 Java 世界见过无数次的故事一模一样：

> ☕ Java 视角：JDBC 之前，Java 连数据库要为每家数据库写私有适配；JDBC 定了 `Connection/Statement/ResultSet` 契约后，数据库厂商写驱动、应用写一次代码，生态直接起飞。更近的类比：USB 之前，键盘是 PS/2、打印机是并口、鼠标是串口——统一接口后，外设数量爆炸。MCP 想做的是同一件事：**工具届的 JDBC / USB**。

MCP 的解法用一句话说：把"宿主应用如何发现工具、如何调用工具、工具如何返回结果"标准化成开放协议。工具方实现一次 MCP server，所有支持 MCP 的宿主都能用；宿主实现一次 MCP client，就能接入所有 MCP server。

## 二、结构：host、client、server 与两种传输

MCP 的核心角色：

```
┌─────────────── host（宿主应用，如 IDE / 你的 Agent）───────────────┐
│  ┌───────── client ─────────┐   ┌───────── client ─────────┐      │
│  │  与 server A 的协议会话   │   │  与 server B 的协议会话   │ ...  │
│  └──────────┬───────────────┘   └──────────┬───────────────┘      │
└─────────────┼──────────────────────────────┼──────────────────────┘
              │  JSON-RPC 消息               │
        ┌─────▼─────┐                 ┌─────▼─────┐
        │ server A  │                 │ server B  │   （每个 server 一组工具）
        │ 文件系统   │                 │  GitHub   │
        └───────────┘                 └───────────┘
```

- **host**：装着大模型的宿主应用。它把各 server 的工具列表汇总进模型的可用工具表
- **client**：宿主内与单个 server 保持的协议会话（一个 server 对应一个 client）
- **server**：独立进程/服务，暴露工具能力。可以是本地进程，也可以是远程服务

一句话记忆：**host 是房东，server 是租户（自带家具=工具），client 是房东给每个租户配的传话门铃。**

两种典型传输（以官方文档为准，细节可能演进）：

| 传输 | 形态 | 适用 |
|---|---|---|
| stdio | server 作为宿主的子进程，标准输入输出上跑 JSON-RPC | 本地工具（文件、本地命令），零网络配置 |
| HTTP（Streamable HTTP） | server 是网络服务 | 团队共享的远程工具、SaaS 化工具 |

> ☕ Java 视角：stdio 传输像你调起一个子进程管道通信（`ProcessBuilder` + stdin/stdout）；HTTP 传输就是一个普通 Web 服务。选择逻辑与"本地函数 vs RPC"完全一致。

## 三、三类原语：tools / resources / prompts

MCP server 不止能暴露"可调用的函数"。协议定义了三类原语（官方定义以 modelcontextprotocol.io 为准）：

1. **tools**：模型可以主动调用的操作（查库、发消息、执行命令）——会改变外部世界或产生计算结果，由模型在推理中决定何时调用
2. **resources**：可供模型读取的数据（文件内容、数据库 schema、日志片段）——类比 REST 里的 GET 资源，由宿主/用户控制挂载
3. **prompts**：可复用的提示模板（如"代码审查提示"）——由用户主动唤起

区分它们的意义在于**权限模型不同**：tools 是"模型主动"，resources/prompts 更偏"用户主动"。这个区分在阶段 4 L03 讲安全时会变得非常重要——模型能主动触发的动作越多，被 prompt injection 劫持后的破坏面越大。

> 🍿 彩蛋｜"MCP 时刻"与生态战：MCP 由 Anthropic 于 2024 年 11 月发布并开源，随后各家宿主应用与工具服务陆续宣布支持。行业里有时把这类"协议一出、生态跟进"的现象叫标准卡位——和当年 REST 战胜一堆私有 RPC、容器编排大战最终 Kubernetes 胜出是同一种剧本：**开发者用脚投票，永远投给"少写适配代码"的那一边**。

## 四、动手：接入一个现成的 MCP server

最快路径（不写代码）：

1. 选一个支持 MCP 的宿主（如支持 MCP 配置的桌面 AI 应用或 CLI 工具，具体以各工具官方文档为准）
2. 在宿主的 MCP 配置里注册一个现成 server——官方与社区维护着一批参考 server（GitHub 仓库 mcp 下的 servers 集合，含文件系统、检索等），配置格式以宿主文档为准
3. 对话中让模型使用该工具，观察宿主如何列出工具、发起调用、回填结果

写代码路径（最小 server 骨架，依赖与 API 以官方文档为准，版本可能更新）：

```python
# 文件头说明：依赖 mcp 官方 Python SDK（GitHub: mcp）；uv pip install "mcp[cli]"
# 以下为 FastMCP 风格的最小 server 骨架，字段/装饰器以官方文档为准
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("note-tools")  # server 名字

@mcp.tool()
def add_note(text: str) -> str:
    """添加一条笔记并返回确认。docstring 就是给模型看的工具说明。"""
    return f"已记录：{text}"  # 真实实现应写入存储

if __name__ == "__main__":
    mcp.run()  # 默认 stdio 传输，供宿主以子进程方式拉起
```

注意两件事：一是**函数签名与 docstring 即 schema**——类型标注生成参数 schema，docstring 成为工具描述，这和你在 Spring 里用注解生成 OpenAPI 文档是同一审美；二是 server 与你的 Agent 主程序**进程隔离**，天然带上了一层权限边界（阶段 4 L03 会展开）。

## 五、MCP 和 function calling 是什么关系

学完阶段 1 再看 MCP，最容易混淆的一对概念。它们不在同一层，互补而不替代：

| | function calling | MCP |
|---|---|---|
| 解决 | 模型 ↔ 你的应用：模型如何"声明要调哪个工具、传什么参数" | 你的应用 ↔ 工具世界：工具如何被发现、接入、调用 |
| 契约在哪 | 模型 API 的调用协议（各家有各家的格式） | 跨应用的开放标准 |
| 工具定义在哪 | 你在应用代码里手写 JSON schema | MCP server 自己描述，宿主自动发现 |
| 类比 | 方法签名（调用格式） | 驱动接口（生态标准） |

串起来看一次完整调用：模型通过 function calling 说"我要调 `search`，参数 `{query: ...}`"（阶段 1 你手写过的部分）→ 你的应用查工具表发现 `search` 来自某个 MCP server → 通过 MCP 协议把调用转发过去（本课新增的部分）→ 结果回填给模型。**前者管模型怎么开口要，后者管工具怎么统一供。**

> ☕ Java 视角：function calling ≈ 你代码里的方法调用语法；MCP ≈ JDBC 驱动层。语法从来不是瓶颈，驱动标准化才是生态爆发点——这就是为什么各家模型 API 的 function calling 格式差异只是小麻烦，而工具接入没有标准曾是大混乱。

## 六、我该用 MCP 吗：三个判断

1. **工具只给自己的一个 Agent 用**：不必上 MCP，内部函数 + schema 就够，少一层协议开销与调试成本
2. **工具要给多个应用/团队用，或想复用社区现成工具**：值得暴露成 MCP server——一次实现，处处接入
3. **你的宿主要接很多异构工具**：直接吃 MCP 生态，别再手写适配层

判断姿态与"要不要上框架"（L01）一脉相承：**协议解决的是复用与生态问题，不是单个应用的性能问题**。另外记住第一条与第三条可以并存：内部工具先写成普通函数，哪天要共享了再包一层 MCP server——协议在边界上，不在函数里。

## 小结与自测

- Q1：MCP 把 N×M 问题变成了什么？怎么变的？
  一句话：变成 N+M——工具方实现一次 server、应用方实现一次 client，通过开放协议对话。
- Q2：host、client、server 三者的关系？
  一句话：host 是宿主应用，为每个 server 维持一个 client 会话，server 是暴露工具的独立进程/服务。
- Q3：tools 与 resources 的关键区别？
  一句话：tools 由模型在推理中主动调用（有副作用或计算），resources 是模型可读的数据（偏用户/宿主控制）。
- Q4：stdio 与 HTTP 两种传输怎么选？
  一句话：本地工具用 stdio（子进程零配置），团队共享/远程工具用 HTTP。
- Q5：什么时候不该用 MCP？
  一句话：工具只服务单个应用时，内部函数足够，协议层是净开销。
