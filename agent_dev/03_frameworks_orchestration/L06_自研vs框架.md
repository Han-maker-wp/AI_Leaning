# 第 6 课：自研 vs 框架——一套决策框架和一句明确的建议

> 🎬 开场钩子：回到第 1 课开头那条 star 曲线：AutoGPT 2023 年 3 月开源后一度是 GitHub 增长最快的项目之一，随后热潮明显退去。退潮的原因里藏着一个对你至关重要的工程事实：大量真实需求最后被证明只需要"一个循环加几个工具"，而框架为想象中的复杂度预支了真实的抽象税。所以本阶段最后一课不教你任何新框架，只教你做决定——并且我会给出明确建议，不和稀泥。

⏱ 建议学时：1.5 小时

## 本课目标

- 用五个维度（迁移成本 / 锁定风险 / 调试透明度 / 功能匹配度 / 团队与维护）给"上框架还是裸写"打分
- 说出"分层混合"策略：哪些层该自己写、哪些层值得借框架
- 记住三条场景化明确建议，并能为自己当前的项目复述决策结论
- 完成 Checkpoint：用 LangGraph 重构阶段 1 迷你 Agent（见本阶段 README）

## 一、五个决策维度

把问题变成可打分的表（1~5 分，倾向框架得高分）：

| 维度 | 问自己的问题 | 倾向框架的信号 | 倾向自研的信号 |
|---|---|---|---|
| 功能匹配度 | 框架现成能力与需求的重合度？ | 需要的（循环/审批/流式）它都有 | 只用到它 10% 的功能 |
| 迁移成本 | 换掉它要改多少代码？ | 抽象接口标准、可整体替换 | 深度依赖其私有抽象 |
| 锁定风险 | 它停更/改协议/改授权，你疼不疼？ | 生态大、开源治理健康 | 单一公司私有 API，社区薄 |
| 调试透明度 | 出问题时，你能在几层抽象内定位？ | 日志/追踪支持完善 | 关键路径要读框架源码才能排障 |
| 团队与维护 | 谁来维护这层依赖？ | 团队有人熟、文档全 | 全组没人读过它的源码 |

两个高频误区：

- **只算功能匹配度，不算调试透明度**。框架的 demo 都很顺，生产事故都发生在抽象层的缝隙里。LLM 应用尤其如此：行为不可复现 + 抽象层数多 = 排障地狱
- **把"用框架"当成能力问题**。事实相反：能裸写的人用框架才安全（L01 的结论）；只会框架的人被框架的默认行为绑架而不自知

### 一个完整打分示例（以"个人知识管家"毕业项目为例）

| 维度 | 打分（1-5） | 一句话理由 |
|---|---|---|
| 功能匹配度 | 4 | 需要"检索→生成→存笔记（审批）"，LangGraph 现成 |
| 迁移成本 | 4 | 编排层独立，业务在纯函数里，可整体替换 |
| 锁定风险 | 4 | 开源、生态大、社区活跃 |
| 调试透明度 | 3 | 图结构与日志可观测，但中断恢复细节要读文档 |
| 团队与维护 | 3 | 一人项目，靠自己啃文档 |

总分 18/25，且没有任何一项是 1~2 分的"红线项"——结论：编排层上 LangGraph，其余按分层策略走。**注意打分的用法：红线项（≤2 分）一票否决比总分更有信息量**——比如"调试透明度 2 分 + 关键路径"就该直接放弃这个框架。

> ☕ Java 视角：这套表你在技术选型时早就打过一遍：Spring Cloud vs 自建微服务、上某云专有 SDK vs 走开源标准。核心永远是同一条：**为确定性付抽象税可以，为想象中的复杂度付抽象税不行**。

## 二、分层混合：这不是二选一

成熟的答案几乎都是分层的。一个典型 Agent 服务可以切成四层，各层独立决策：

```
┌─ 编排层（循环/分支/审批）   → LangGraph 或自研状态机，二选一
├─ 单步调用层（调模型/解析）  → 薄封装：官方 SDK + 结构化输出，通常自研
├─ 工具层（业务能力）        → 永远自研；对外共享时包成 MCP server（L04）
└─ 观测评估层（日志/追踪/回归）→ 自研数据格式 + 开源工具渲染（阶段 4 展开）
```

分层的价值：**锁定风险被限制在单层内**。哪天 LangGraph 不合用了，换掉编排层，工具层、观测层原封不动——这正是你在 Java 里用接口隔离第三方依赖的同一招。这张四层图也回答了一个经典问题"我这是不是在重复造轮子"：看清楚——你造的从来是轮子之间的传动轴，轮子（模型、框架）别人造得比你好。

> 🍿 彩蛋｜Karpathy 的"LLM OS"设想：2023 年，Andrej Karpathy 提出一个广为流传的设想——大模型是 CPU，上下文窗口是内存，工具是外设，Agent 框架则是这之上的"操作系统"。按这个类比看框架之争就通透了：操作系统会沉淀（值得用现成的），但没人会因为换操作系统重写自己的应用程序（你的业务工具层永远是你自己的）。

## 三、明确建议（按场景背下来）

1. **学习期（就是现在的你）**：核心循环必须裸写过一遍（已完成 ✓），然后必须至少用一个框架重构一遍（本课 Checkpoint）——两个都做过，你才有资格谈选型
2. **原型期 / 内部工具**：直接上框架（LangGraph 起手），快就是一切；但把业务逻辑写在框架无关的纯函数里，给将来"抽走框架"留好缝
3. **生产期**：编排层可用 LangGraph（锁定风险已被分层控制），单步调用层自研薄封装，工具层永远自研；任何进入关键路径的框架行为（重试、历史裁剪、schema 注入）都要显式配置并写进回归测试（阶段 4 L02 接上）

三阶段速查：

| 你在哪 | 编排层 | 单步调用层 | 工具层 |
|---|---|---|---|
| 学习期 | 裸写一遍 → 再用框架重构一遍 | 裸写（理解协议） | 裸写 |
| 原型期 | 框架（快） | 框架（省事） | 自研（业务跑不掉） |
| 生产期 | 框架或自研（按五维表） | 自研薄封装 | 自研 + 需要共享时包 MCP |

（这个表本身就是你的"血肉清单"：无论哪一行，工具层那一格永远是"自研"。）

一句话版：**框架管骨架，自研管血肉；骨架可换，血肉永远是你的。**

## 四、迁移预案：假设三个月后要换掉它

决策做完不等于锁死。给"上框架"的决定配一份迁移预案，锁定风险就从"信仰问题"变成"工程问题"。写进项目 README 的四条：

1. **依赖收口**：框架的导入只允许出现在编排层文件里，其余代码（工具、业务逻辑、观测）零框架导入——换框架时物理上只动一个目录
2. **测试护城河**：阶段 4 L02 的评估集跑在"框架无关"的接口上（输入问题 → 输出回答），换实现不改评估——这是你敢换的底气
3. **抽象薄垫**：编排层暴露给自己的接口只有两三个函数（如 `run_agent(question) -> answer`），上游服务不感知底下是 LangGraph 还是自研
4. **弃用触发器**：预先写下"什么时候该启动迁移"的具体信号（如：某关键 bug 官方三个月未修 / 破坏性升级导致回归超过一周工作量），避免"忍到爆炸"

> ☕ Java 视角：这就是你熟悉的"防腐层"（anti-corruption layer）手艺：第三方依赖永远包在自己的接口后面。没有人会因为换数据库重写全部业务代码——前提是从第一天就没人让 SQL 满天飞。

> 🍿 彩蛋｜"demo 驱动开发"的黑话：行业里把"拿 demo 效果做技术决策"戏称为 demo-driven development——AutoGPT 热潮期最典型的决策方式：周末跑通一个自主任务 demo，周一就宣布全面转型 AI 原生。你作为经历过各种"中台热、微服务热"的 Java 老兵，对这种剧本应该有肌肉记忆：**热度是选型信号里最不值钱的一个**。

## 五、Checkpoint 提示（本阶段验收）

用 LangGraph 重构阶段 1 迷你 Agent 的完整要求见本阶段 README。三个容易翻车的点提前提醒：

1. 状态设计先想清楚哪些字段要 reducer（历史累加）哪些不要（计数快照）——L03 的 2.1 节
2. 循环上限放进路由函数，别在节点里偷偷 break——图里没有 break，只有"走向哪条边"
3. 对比报告别写成"框架真方便"，要具体到：加一个新工具各改几行？中断恢复各要做什么？——那是 L06 决策表的一手证据
4. 顺手完成 ADR-001（第六节模板）——重构本身就是你第一份决策记录的"背景"段落

## 六、决策记录模板（ADR 一页版）

把你这次选型写成一份迷你 ADR（Architecture Decision Record）存进仓库 `docs/adr-001-orchestration.md`。五段式：

```markdown
# ADR-001：编排层选型

## 背景（为什么现在要做这个决定）
两句话：项目要什么、约束是什么。

## 决定（一句话结论）
编排层采用 LangGraph；单步调用层自研薄封装；工具层自研。

## 理由（五维表摘要 + 红线项检查）
总分 x/25，无红线项；最担心的维度是 ___，缓解措施是 ___。

## 后果（得到了什么、放弃了什么）
得到：循环/审批/中断恢复的现成实现。放弃：对执行细节的完全掌控。

## 弃用触发器（何时重开此决策）
见"迁移预案"第 4 条的具体信号。
```

为什么值得写：三个月后有人（包括未来的你）问"当初为什么选它"，你掏出的是有依据的文档而不是"当时挺火的"。**选型不可怕，可怕的是说不清为什么。**

## 练习

1. 用第一节的五维表，为你毕业项目（阶段 4 L05 三选一后）打分，写出每格 1~5 分和一句理由。
   提示：先写"功能匹配度"，你最清楚自己要循环还是要流水线。
2. 对你的项目画出第二节的四层结构图，标注每层的"自研/框架/开源工具"决定。
   提示：工具层和观测层的答案几乎总是"自研"，重点纠结编排层即可。
3. 写一段 100 字的"选型备忘"：如果三个月后要向团队解释为什么这么选，你怎么说？
   提示：用"骨架/血肉"的分层论证，比"框架好用/不好用"有说服力得多。
4. 按第六节模板为你的项目写 ADR-001，其中"弃用触发器"必须写出两个具体信号。
   提示：好的触发器是可观测的事实（回归耗时、bug 响应时长），不是情绪（"感觉不顺手"）。

## 小结与自测

- Q1：五个决策维度里最容易被忽略的是哪个？
  一句话：调试透明度——demo 阶段感知不到，生产事故时才付账。
- Q2：分层混合策略的四层是什么？哪层永远自研？
  一句话：编排/单步调用/工具/观测评估四层；工具层（业务能力）永远自研。
- Q3：生产期对框架的默认行为应该什么态度？
  一句话：显式配置关键默认值（重试/裁剪/schema 注入）并纳入回归测试。
- Q4：为什么"裸写过一遍"是用框架的前提？
  一句话：懂机制才能识别框架的默认行为何时在坑你（也是排障的底气）。
- Q5：迁移预案的四条是什么？
  一句话：依赖收口、测试护城河、抽象薄垫、弃用触发器——把"锁定风险"变成可管理的工程问题。
