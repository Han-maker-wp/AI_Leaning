# 第 1 课：可观测性——先让 Agent "开口说话"

> 🎬 开场钩子：凌晨两点，用户反馈 Agent 给了个离谱答案。你打开日志，grep 半天只找到一行 `ERROR: something failed`——没有上下文、没有调用链、没有 token 记录，甚至不知道那次回答调了几次模型。传统服务里你能靠"同输入同输出"复现排查；LLM 应用里这条退路也被堵死：同样的输入，两次运行可能给出不同输出。**没有可观测的 Agent，出了问题等于失明。** 本课是工程化四件套的第一件，也是最优先的一件。

⏱ 建议学时：2.5 小时

## 本课目标

- 说出 LLM 应用可观测与传统服务可观测的三个差异点
- 给 Agent 加上结构化日志：每次模型调用记录 trace_id、token 用量、延迟
- 用 span 树描述一次请求的完整调用链，并手写一个最简 tracer（纯标准库）
- 建立成本视图：每次回答花了多少 token、多少钱，p50/p95 延迟各是多少

## 一、为什么这是"新问题"：四个差异点

| 维度 | 传统 Web 服务 | LLM Agent |
|---|---|---|
| 输出确定性 | 同输入同输出，可复现 | 温度>0 时不可复现，排查必须靠"当时记录" |
| 单请求链路 | 通常 1 次主要计算 | N 次模型调用 + M 次工具调用，嵌套且带循环 |
| 成本模型 | CPU/内存，边际近零 | 每一步都按 token 真金白银计费 |
| 失败形态 | 抛异常，监控告警 | "软失败"：正常返回但答案错了，没有任何报错 |

第四点最阴险：**Agent 不会为错误答案抛异常**。所以可观测的对象不止"错误"，还有"质量信号"——这要等第 2 课的评估来补，本课先把"发生了什么"记全。

## 二、结构化日志：从"给人看"到"给程序看"

原则：每条日志是一个 JSON 对象（字段化），而不是一串自由文本。Agent 最小字段集：

- `ts`（时间戳）、`level`、`event`（事件类型：llm_call / tool_call / final_answer）
- `trace_id`（贯穿一次用户请求）、`span_id`（本次子调用）
- `model`、`prompt_tokens`、`completion_tokens`、`latency_ms`
- `error`（若有）

> ☕ Java 视角：这就是 logback 换 JSON encoder、日志平台按字段检索的世界；`trace_id` 贯穿请求等于 MDC（Mapped Diagnostic Context）——只是 Python 里用标准库 `contextvars` 实现（线程/协程安全地携带请求级变量，比 ThreadLocal 更适配 asyncio）。

完整可运行的最小实现（纯标准库，不需要任何依赖）：

```python
# 文件头说明：纯标准库演示，无需安装依赖、无需 API key
import json
import logging
import time
import uuid
import contextvars

trace_id_var: contextvars.ContextVar[str] = contextvars.ContextVar("trace_id", default="-")


class JsonFormatter(logging.Formatter):
    """把 LogRecord 序列化成单行 JSON——给日志平台看的格式"""

    def format(self, record: logging.Message) -> str:
        payload = {
            "ts": self.formatTime(record),
            "level": record.levelname,
            "trace_id": trace_id_var.get(),
            "event": record.name,
            "msg": record.getMessage(),
        }
        if hasattr(record, "extra_fields"):
            payload.update(record.extra_fields)  # 结构化字段平铺进同一条 JSON
        return json.dumps(payload, ensure_ascii=False)


def get_logger(name: str) -> logging.Logger:
    logger = logging.getLogger(name)
    if not logger.handlers:
        handler = logging.StreamHandler()
        handler.setFormatter(JsonFormatter())
        logger.addHandler(handler)
        logger.setLevel(logging.INFO)
    return logger


def call_llm(prompt: str) -> dict:
    """mock 一次模型调用：真实项目在此记录 API 返回的用量字段"""
    log = get_logger("llm_call")
    start = time.perf_counter()
    time.sleep(0.05)  # 假装在等 API
    usage = {"prompt_tokens": len(prompt) // 2, "completion_tokens": 42}
    log.info("llm call done", extra={
        "extra_fields": {"model": "mock-model", "latency_ms": round((time.perf_counter() - start) * 1000, 1),
                         "prompt_tokens": usage["prompt_tokens"],
                         "completion_tokens": usage["completion_tokens"]}})
    return {"text": "（mock 回答）", "usage": usage}


def main() -> None:
    trace_id_var.set(str(uuid.uuid4())[:8])  # 一次用户请求一个 trace_id，所有日志可聚合
    log = get_logger("agent")
    log.info("user request received", extra={
        "extra_fields": {"user_input_len": 18}})
    result = call_llm("帮我总结这段文档……")
    log.info("final answer", extra={
        "extra_fields": {"answer_len": len(result["text"]),
                         "total_tokens": sum(result["usage"].values())}})


if __name__ == "__main__":
    main()
```

跑起来每行都是可 `jq` 解析的 JSON。上线前再补两件事：敏感字段脱敏（第 3 课）、日志落文件/平台（运维常识，不展开）。

> 🍿 彩蛋｜可观测"三支柱"：行业黑话里 observability 三支柱 = logs（日志）、metrics（指标）、traces（追踪）。你在 Java 世界已经齐装满员（ELK + Micrometer + SkyWalking/Zipkin 那一套）；LLM 应用要多加一根 unofficial 的第四柱——**evals（评估数据）**，因为"答案质量"是传统三支柱测不到的。

## 三、Tracing：一次请求长成一棵树

结构化日志回答"每一步发生了什么"，tracing 回答"这些步骤怎么嵌套、谁最慢、谁最贵"。一次用户请求的典型 span 树：

```
trace: a3f8（用户问："这份合同有什么风险？"）
└─ span: agent_run                    3200ms   $0.012
   ├─ span: retrieve   （RAG 检索）    400ms   $0.000
   │  ├─ span: embed               150ms
   │  └─ span: vector_search       220ms
   ├─ span: llm_call #1（决策调工具） 900ms   $0.004
   ├─ span: tool: search_clause     300ms
   ├─ span: llm_call #2（生成答案）  1500ms   $0.008
   └─ span: guard_check              20ms
```

有了这棵树，"慢在哪、贵在哪"一眼可见：上面 60% 延迟在两次模型调用，66% 成本在最后一次——优化对象自动浮现。

现成工具两档：**通用标准** OpenTelemetry（Span API 跨语言，可对接你公司已有的 APM）；**LLM 专用** LangSmith、Langfuse 等（名字仅作检索线索，不给 URL，选型前自行尽调）。无论用哪档，**数据格式自己定义在先**（字段：span 名、起止、token、成本），工具只是渲染层——这是 L06 分层策略在观测层的应用。

> ☕ Java 视角：span 树就是分布式追踪里你熟悉的那个调用链瀑布图（Zipkin/Jaeger UI 里的瀑布），连"找最慢 span"的用法都一样。差异只有一个：LLM span 上多两个一等公民字段——token 与成本。

## 四、成本与延迟：给每次回答记账

两条纪律：

1. **每次模型调用都记录 usage 字段**（prompt/completion tokens，API 返回里有），按各模型单价换算成本——单价以各厂商官方定价页为准，硬编码单价表要带更新日期
2. **用分位数看延迟**：平均值会被长尾骗，报 p50/p95（"一半请求快于 X、95% 请求快于 Y"）。并发下还要记录重试次数——限流重试是延迟尖刺的头号来源

最小记账结构（接第二节的日志即可）：

```python
# 文件头说明：纯标准库演示，接在第二节日志体系之上
from dataclasses import dataclass, field


@dataclass
class CostTracker:
    """按 trace 聚合一次请求的成本与延迟（真实项目挂在 span 树根节点上）"""
    model_prices: dict[str, tuple[float, float]] = field(
        default_factory=lambda: {"mock-model": (0.5 / 1_000_000, 1.5 / 1_000_000)})  # 每千 token 输入/输出价（mock 值）
    total_tokens: int = 0
    total_cost: float = 0.0

    def add(self, model: str, prompt_tokens: int, completion_tokens: int) -> None:
        p_in, p_out = self.model_prices[model]
        self.total_tokens += prompt_tokens + completion_tokens
        self.total_cost += prompt_tokens * p_in + completion_tokens * p_out

    def summary(self) -> str:
        return f"tokens={self.total_tokens}, cost=${self.total_cost:.6f}"


def main() -> None:
    tracker = CostTracker()
    tracker.add("mock-model", 1200, 300)
    tracker.add("mock-model", 800, 150)
    print(tracker.summary())  # tokens=2450, cost=$0.00XXXX —— 一次回答的账单


if __name__ == "__main__":
    main()
```

> 🍿 彩蛋｜"here1 / here2"考古：每个工程师都写过 `System.out.println("here1")`。它和现代可观测的差距，就是"当时我在哪"与"整个系统每一步在哪、花了多少"的差距。LLM 时代这笔账更狠：调试一次盲飞的重放，烧掉的 token 可能比上线一天的用量还多——**可观测不是奢侈品，是省钱手段**。

## 小结与自测

- Q1：LLM 应用可观测与传统服务的四个差异点？
  一句话：输出不可复现、链路多步嵌套、每步按 token 计费、失败是软失败（不抛异常）。
- Q2：`trace_id` 的作用与 Python 实现机制？
  一句话：贯穿一次请求聚合所有日志；标准库 `contextvars`（协程安全的 MDC）。
- Q3：span 树能回答哪两个传统日志难回答的问题？
  一句话：哪一步最慢（延迟瀑布）、哪一步最贵（成本分布）。
- Q4：为什么延迟要看 p95 而不是平均值？
  一句话：长尾请求被平均掩盖，p95 暴露大多数用户的真实体验下限。
- Q5：为什么说可观测是省钱手段？
  一句话：盲飞排查靠反复重放烧 token，记录一次全链路信息可离线分析。
