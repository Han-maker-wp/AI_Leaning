## 一、FastAPI：Spring Boot 熟悉的配方

FastAPI 是 Python 世界最像 Spring Boot 的框架：注解式路由、声明式校验、自动 API 文档。最小对照：

> ☕ Java 视角：`@app.post("/chat")` ≈ `@PostMapping("/chat")`；Pydantic 模型 ≈ DTO + Bean Validation（`Field(min_length=1)` ≈ `@NotBlank`）；访问 `/docs` 自动出现 Swagger UI ≈ springdoc-openapi，区别是 FastAPI **自带**，不用加依赖。写惯 Spring 的人上手 FastAPI 的速度会快得不好意思。

配套代码 `code/L04_fastapi_server.py` 的契约层（节选）：

```python
# 文件头说明：依赖 fastapi、uvicorn（uv pip install fastapi uvicorn），以官方文档为准
from pydantic import BaseModel, Field
from fastapi import FastAPI

app = FastAPI(title="agent-service")

class ChatRequest(BaseModel):
    """请求契约：字段校验失败自动返回 422 + 明确错误信息（相当于 @Valid）"""
    message: str = Field(min_length=1, max_length=4000)
    session_id: str | None = None   # Python 3.10+ 联合类型语法

class ChatChunk(BaseModel):
    delta: str          # 本段新增文本
    done: bool          # 是否最后一块
```

两个必须做的端点习惯（从 Spring 时代带过来的）：`/health` 健康检查给负载均衡探活；422 校验错误让调用方拿到结构化报错而不是 500。

## 二、async 的真实意义：别让一个请求饿死所有人

FastAPI 里 `async def` 端点跑在单线程事件循环上（uvicorn）。Agent 服务的特殊性：**一次回答 = 数秒的模型等待**，这正是 IO 密集场景，异步收益极大——但要遵守两条铁律：

1. 端点内等待外部 IO（模型 API、数据库）用 `await`，让出事件循环
2. 万一要跑 CPU 密集或会**阻塞**的同步 SDK 调用，扔进线程池（`run_in_executor` 的思路），否则一个慢调用饿死所有并发请求

> ☕ Java 视角：事件循环模型 ≈ Netty 的单线程 EventLoop：不能在 IO 线程上做重活。Java 后来用虚拟线程（Loom）绕开了这套心智负担，asyncio 仍是 Python 侧的主流答案——好在 Agent 服务 95% 的时间在等模型响应，纯 IO，`async def` + `await` 就够了。

## 三、流式输出：SSE 为什么赢了

用户盯着空白页面等 8 秒会怀疑服务挂了；流式打字机输出把"感知延迟"从 8 秒压到 1 秒内。技术上两条路：

| | SSE（Server-Sent Events） | WebSocket |
|---|---|---|
| 方向 | 单向（服务器 → 客户端） | 双向 |
| 协议 | 纯 HTTP | 升级协议 |
| 基础设施 | 网关/代理/负载均衡全兼容 | 需要专门支持 |
| 适用 | LLM 流式回答（就是它） | 实时双向（协作编辑、语音） |

LLM 回答是典型的单向流——**SSE 完胜**：请求还是普通 POST，响应头 `Content-Type: text/event-stream`，正文按 `data: {...}\n\n` 分块推送。这也是主流大模型 API 采用的方式。

服务端的 SSE 帧长这样（`code/L04_fastapi_server.py` 的输出格式）：

```
data: {"delta":"（moc","done":false}

data: {"delta":"k 回答","done":false}

data: {"delta":"","done":true}

```

三个协议细节（解析时最容易踩的坑）：每条消息以 `data: ` 开头（注意冒号后的空格）；**空行是事件分隔符**，解析器必须跳过；事件可以带 `event:`/`id:` 等字段，最小实现里用不到但别当它们是错误。

> 🍿 彩蛋｜SSE 的翻身仗：Server-Sent Events 是 HTML5 时代的"老古董"，当年被 WebSocket 抢尽风头——谁都要双向嘛。LLM 流式输出让它意外翻红：模型回答只需要服务器往客户端单向推字，现成的 HTTP 基础设施一点不用改。老技术的胜利往往不靠更强，靠**刚好匹配新场景的形状**。

> ☕ Java 视角：Spring 里的 `SseEmitter` 就是这东西的 Java 面孔。而消费端更简单——JDK 11 起 `java.net.http.HttpClient` 原生就能流式读响应体，不需要任何第三方库（见 `code/L04_java_client.md`）。

## 四、会话状态与水平扩展

多轮对话的状态（历史消息）放哪？**不放进程内存**。进程内存里的会话在水平扩展（多实例）和重启（发版）时全部蒸发。老规矩：

- 服务本身无状态（stateless），任何实例可处理任何请求
- 会话状态放外部存储：开发期 SQLite/文件，上量后 Redis/数据库，按 `session_id` 存取
- 每次请求带上 `session_id`，服务端取历史 → 追加本轮 → 写回
- 状态外置还有个隐藏收益：重启不丢上下文，灰度发版时新旧版本可以共读同一份会话

这与"Session 外置到 Redis、服务才能加机器"是同一课——你甚至可以把 Spring Session 的心智图直接画过来。

## 五、部署要点（一页清单）

1. **入口**：`uvicorn` 启动（开发 `uvicorn main:app --reload`，生产多 worker 以官方文档为准）；FastAPI 应用只是 ASGI 协议上的一个可调用对象——概念上 ≈ Servlet 跑在 Tomcat 上
2. **容器化**：Docker 打包（Python 基础镜像 + 依赖锁定文件），与 Java 世界 jar → 镜像同一套路
3. **配置**：API key、模型名等走环境变量注入，绝不进代码库（第 3 课的安全清单项）
4. **观测**：接第 1 课的结构化日志输出到 stdout，由日志平台收集
5. **超时与降级**：模型调用设上限超时；超限返回结构化错误而非挂死网关

## 六、错误处理：给"会思考的后端"定错误码

Agent 服务的错误分三层，处理策略完全不同（都是你的老手艺）：

| 层 | 典型错误 | HTTP 语义 | 客户端该做什么 |
|---|---|---|---|
| 请求层 | 参数校验失败、超长输入 | 422 / 413 | 修请求，别重试 |
| 依赖层 | 模型 API 限流/超时/5xx | 503 + `retry_after` | 指数退避重试（仅幂等场景） |
| 质量层 | 模型拒答、工具被门禁拦截 | 200 + 业务字段说明 | 读业务码决定展示话术 |

第三层最值得强调：**"工具被安全门禁拦截"不是系统错误，是正常业务结果**——返回 200 并在响应体里带结构化原因（"该操作需人工审批"），比抛 500 客户友好得多。你的 Java 直觉在这里完全适用：系统异常和业务异常从来就是两码事。

> ☕ Java 视角：这就是 `@ControllerAdvice` 统一异常处理 + 错误码枚举的 Python 版。FastAPI 的异常处理器（exception handler）注册机制对应 `@ExceptionHandler`，用法以官方文档为准。

## 小结与自测

- Q1：FastAPI 里 Pydantic 请求模型承担什么职责？
  一句话：DTO + 参数校验（失败自动 422），契约即文档（自动生成 OpenAPI）。
- Q2：async 端点里最忌讳什么？
  一句话：同步阻塞调用（阻塞 SDK/CPU 密集活）占住事件循环，饿死所有并发请求。
- Q3：LLM 流式为什么选 SSE 而不是 WebSocket？
  一句话：回答是单向流，SSE 纯 HTTP、基础设施全兼容，无需双向能力。
- Q4：会话状态为什么必须外置？
  一句话：水平扩展（多实例共享）与重启存活（发版不丢会话）都要求服务无状态。
- Q5：uvicorn 和 FastAPI 的关系？
  一句话：FastAPI 是应用框架，uvicorn 是 ASGI 服务器（≈ Tomcat 之于 Servlet）。
