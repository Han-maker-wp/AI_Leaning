# 第 5 课：毕业项目——三选一，全流程走一遍

> 🎬 开场钩子：BabyAGI——那个启发了一整代多 Agent 工具的项目——是 Yohei Nakajima 2023 年 4 月的一个周末作品。不是财团资助，不是大厂立项，就是一个会写代码的人把想清楚的东西在两天里做了出来。你现在手里的积累（手写循环、RAG、编排、观测、评估、安全、部署）已经远超"一个周末"的门槛。这一课只有一个任务：把它拧成一个完整、能跑、敢给人看的作品。

⏱ 建议学时：2-3 周（里程碑见下）

## 本课目标

- 三选一确定项目，写出 1 页需求说明书（用户、场景、明确不做什么）
- 产出设计文档：架构图 + 工具清单 + 分层决策（引用 03 阶段 L06）
- 实现：可运行代码 + README（三条命令内跑起来）
- 评估：≥20 条评估集 + 基线报告 + 上线判据（引用本阶段 L02）
- 部署：FastAPI 服务化 + 流式端点 + Java 客户端演示（引用本阶段 L04）

## 一、三选一项目规格

### A. 个人知识管家

- **一句话**：把本地文档文件夹变成"带引用的问答助手 + 笔记沉淀工具"
- **核心需求**：文档接入（md/txt/pdf）；RAG 问答且每条回答标注来源文件与片段；"存为笔记"工具（可逆写操作，过门禁）
- **技术要点**：切块与检索质量是成败关键（阶段 2 手艺 + faiss/chromadb 任选）；引用溯源要在提示里强制"只依据检索内容作答"
- **加分项**：把"笔记工具"包成 MCP server（03 阶段 L04）；笔记去重合并
- **适合**：文档多、想每天真用的人——**最能长期吃自己狗粮**

### B. 自动化办公 agent

- **一句话**：读邮件/日程/待办，生成回复草稿与日程摘要，高危操作一律人工审批
- **核心需求**：三个读工具（邮件、日程、文档检索）+ 两个写工具（草稿箱、发件），"发送"必须过审批流（03 阶段 L03 的 review 节点）
- **技术要点**：工具分级门禁（本阶段 L03）；mock 数据即可，不必真连邮箱——评委看的是门禁与审批，不是 SMTP
- **加分项**：审批支持"驳回并带修改意见"回到 agent 重写；日预算限制（每天最多发 N 封）
- **适合**：想展示"Agent + 真实权限边界"工程判断力的人——**面试叙事最硬**

### C. 领域客服

- **一句话**：限定领域（如某产品售后）的客服：知识库问答 + 工单查询 + 超纲拒答转人工
- **核心需求**：RAG 知识库；工单查询工具（读操作）；超纲问题明确说"转人工"而不是硬编；对抗鲁棒性（诱导泄露提示词、绕过审批类输入全部挡住）
- **技术要点**：评估集里对抗类别占比 ≥15% 且通过率必须 100%（本阶段 L02/L03 联动）；回答延迟 p95 目标自定并写进上线判据
- **加分项**：多轮上下文（会话外置存储）；满意度模拟评分
- **适合**：想要"最接近生产"完整体验的人——**工程化要求最全面**

> ☕ Java 视角：这就是一次浓缩版的"从需求评审到上线复盘"完整 sprint——你带过项目的话，所有流程肌肉记忆都在：范围控制（明确不做什么）、契约先行（工具 schema 与 API 设计）、门禁（评估与审批）、灰度（上线判据）。Agent 项目没发明任何新项目管理学。

## 二、统一里程碑（建议 2.5 周）

| 里程碑 | 时长 | 交付物 | 对应课程 |
|---|---|---|---|
| M1 需求 | 0.5 周 | 1 页说明书：目标用户、3 个核心场景、"明确不做"清单 | 全轨道 |
| M2 设计 | 0.5 周 | 架构图（四层：编排/调用/工具/观测）+ 工具清单与分级表 + 技术选型决策记录 | 03 L06 |
| M3 实现 | 1 周 | 可运行代码 + README（三条命令内跑通）+ 结构化日志 | 03 全阶段 + 04 L01 |
| M4 评估 | 0.5 周 | ≥20 条评估集（含对抗）+ 基线通过率报告 + 失败条目分析 | 04 L02 |
| M5 部署 | 0.5 周 | FastAPI 服务（含流式）+ 安全清单落地核对 + 演示脚本 | 04 L03/L04 |

里程碑纪律：**每个 M 结束打一次 tag/存档**，不允许"实现还没完就开始改设计"的滚动式模糊——评委会按里程碑查交付物。

> 🍿 彩蛋｜简历驱动开发（resume-driven development）：行业黑话，指"为了让简历好看而堆技术"的开发方式——毕业项目最容易犯的病：上三个框架、五个 Agent，核心问答却答不准。反过来想：**简历上最值钱的不是技术名词清单，是"我把通过率从 60% 提到 85% 的过程"这种有数字的叙事**——后者只有 evals 能给你。

## 三、统一验收标准（硬性）

**功能与工程：**

1. 陌生人拿到仓库，按 README **三条命令内**跑起来（含依赖安装）
2. 服务化：`/health` + 非流式 + 流式三端点可用，Java 客户端能完成一次流式调用（04 L04 的配套代码可直接改造）
3. 可观测：任一次回答能给出"调了几次模型/工具、耗时分布、token 成本"（04 L01）
4. 安全：工具全过分级门禁；高危操作有人工确认路径；出站内容脱敏；对抗条目 100% 通过（04 L03）

**质量与评估：**

5. 评估集 ≥20 条（常规 ≥12 / 边界 ≥5 / 对抗 ≥3），judge 与人工抽检 20 条一致率 ≥80%（04 L02）
6. 验收问题 10 个（自拟、覆盖三类），现场演示答对/合格 ≥8 个
7. 有一份"改动前后对比"记录：至少一次真实的优化迭代（改 prompt/检索参数）前后通过率对比

**文档：**

8. README 含：项目一句话、快速开始、架构图链接、评估报告摘要、已知限制（诚实列出）

## 四、分项目验收要点

| 项目 | 必验项 | 不合格红线 |
|---|---|---|
| A 知识管家 | 10 个问题中 ≥8 个回答带正确引用（能定位到文件与片段） | 编造引用（引了不存在的内容） |
| B 办公 agent | 全流程演示：读邮件→草稿→审批→（驳回→修改）→发送 | 未经审批触达任何"发送"路径 |
| C 领域客服 | 15 问中 ≥12 合格 + 3 个对抗输入全部正确拒绝/转人工 | 超纲问题硬编；泄露系统提示词 |

## 五、常见坑（前人尸检报告）

1. **M1 不写"明确不做"** → 范围无限膨胀，M5 变 M15。1 页纸写不完的需求就是超纲的需求
2. **先写代码后定评估** → 交付前才发现通过率不可测，没有基线就没有"优化"叙事。M2 就要把 10 个验收问题拟好
3. **检索质量怪模型** → 知识类项目答不准，九成是切块/检索问题（阶段 2 的教训），先修检索再动 prompt
4. **mock 数据太假** → 评审演示时数据不像真的，可信度崩塌。花半小时造 20 条像样的样例数据
5. **README 只写给自己** → 检验标准：让没参加过你项目的同事只靠 README 跑——过不了就是不合格

> 🍿 彩蛋｜AutoGPT 的教训再读一遍：它 2023 年 3 月开源后一度是 GitHub 增长最快的项目之一，但热潮退去后留下的真正资产，是被它吸引进场的工程师们沉淀的工程认知。你的毕业项目反过来做：**不需要增长曲线，需要的是 10 个问题里答对 8 个的确定性**——demo 让人惊叹，确定性让人敢用。

## 六、卡住了怎么办（按里程碑给处方）

- **M1 就选不出来**：默认选 A（知识管家）——数据你最熟、最容易吃狗粮；B 和 C 的亮点（审批流、对抗防御）都能做成 A 的加分项
- **M3 一周写不完**：砍工具数量，不砍里程碑。三个工具 + 完整评估，好过八个工具没有评估——验收表里 M4 的权重救过所有人
- **M4 通过率惨不忍睹**：先给失败条目分类（检索失败 / 工具选错 / 生成跑偏），只修占比最大的一类。40% → 70% 是正常工作量；40% → 95% 不是
- **M5 部署环境出幺蛾子**：mock 模式保底演示——评委要看的是服务形状与门禁，真实模型调用可以录屏补

## 七、十分钟演示脚本（验收/答辩通用）

1. **0-2 分钟 讲需求**：M1 说明书的三场景 + 一句话"明确不做"
2. **2-4 分钟 走架构**：四层图 + 工具分级表 + ADR 结论（03 阶段 L06 的产出）
3. **4-7 分钟 现场演示**：3 个核心场景 + 1 个对抗输入被挡下的瞬间（全场高光，提前排练）
4. **7-9 分钟 讲证据**：评估报告——基线 → 优化 → 通过率对比，附成本与延迟数字（04 阶段 L01/L02 的产出）
5. **9-10 分钟 讲限制**：诚实列出已知边界与下一步——敢说限制的项目比声称完美的项目可信十倍

> ☕ Java 视角：这套结构就是你参加过的技术评审：问题 → 方案 → 演示 → 数据 → 风险。Agent 项目没有发明新的汇报学。

## 练习

1. 写出 M1 的 1 页需求说明书（今天就写）：三个核心场景 + 五条"明确不做"。
   提示：三选一犹豫时，选你未来三个月会真实使用的那个——狗粮是最好的迭代驱动力。
2. 列出你的工具分级表：每个工具一行（名称/级别/白名单/是否需审批），空表也要交。
   提示：对照 04 L03 的三级划分；没有危险工具的项目要说明"为什么不设"。
3. 拟定 10 个验收问题与 3 个对抗输入（M2 交付物），先于任何代码。
   提示：对抗输入从 04 L02 的对抗类别模板改造，必须针对你项目的真实高危路径。
4. 给自己排期：按里程碑表填日历，每个 M 预留半天缓冲。
   提示：经验法——M3 实现永远超时 50%，要么砍范围要么认命，别砍 M4。

## 小结与自测

- Q1：三个项目的共同必验项是什么？
  一句话：带评估报告的可运行服务 + 安全门禁 + 三条命令跑通的 README（细节见第三节 8 条硬标准）。
- Q2：为什么验收问题必须在 M2 拟好？
  一句话：没有先定的验收标准就没有客观基线，"优化"叙事无法成立。
- Q3：知识类项目答不准时，第一嫌疑是谁？
  一句话：检索与切块（阶段 2 的老结论），不是模型也不是 prompt。
- Q4：毕业项目与 AutoGPT 式 demo 的本质区别？
  一句话：确定性——10 问 8 中的可复现合格率，而非一次性令人惊叹的演示。
